# Go to SQL type mapping

This page lists which SQL column type Momo uses for each Go field type, what
survives a round trip, and where the edges are. The tables are checked by
tests: `TestTypeMappingDoc` fails when a row here disagrees with the generator's
type map or a codec's `SQLType`, and `TestTypeMapping` creates a column of each
documented PostgreSQL type on a live server, and the generated SQLite type on a
live SQLite database, and round-trips edge values through it.
`TestTypeMappingMySQL` does the same with the MySQL column on MySQL 8.4, MySQL
9.7 and MariaDB 11.8, and `TestTypeMappingMySQLNull`,
`TestTypeMappingMySQLUnsigned` and `TestTypeMappingMySQLLimits` check NULL, the
unsigned types and the MySQL limits.

## How a type is chosen

1. A field whose type implements the codec contract (`types.Codec`: `Scan`,
   `Value` and `SQLType`) uses its own `SQLType`. This is how `types.TimeOfDay`
   and `types.Hstore` get their columns.
2. Otherwise the generator maps the Go type with its built-in table
   (the generator's type map). A pointer and the `sql.Null*` wrappers map like the
   type they wrap: nullability is a column property, not a type property.
3. A Go type with no mapping (for example `uint64` or `map`) makes
   the type map return an error wrapping `momo.ErrUnsupported`, which the
   generator reports at the field. Give the type a codec or declare the column
   yourself.

## Generated mappings

`N` is the `size` tag for `string` and the `dim` tag for vector types. A
`vector.Vector` or `vector.HalfVector` field without `dim` is supported: it maps
to the bare `vector` or `halfvec` type, a dimensionless column that holds
embeddings of any size (see [vectors.md](vectors.md#dimensionless-columns)).
`vector.SparseVector` and `vector.Bits` require `dim`. SQLite has no vector
types.
A slice of a scalar maps to the PostgreSQL array of its element type; SQLite
has no array columns, so the generator rejects them there.

The MySQL column is what the type map returns for MySQL and MariaDB, which share
it. Unsigned Go integers map to the unsigned column types: `uint8` to
`tinyint unsigned`, `uint16` to `smallint unsigned`, `uint32` to `int unsigned`,
`uint` to `bigint unsigned` and `uint64` to `bigint unsigned`. `int8` maps to
`tinyint`, and `bool` to `tinyint(1)`. A `vector.Vector` column needs MySQL 9.0
or MariaDB 11.7; MySQL 8.4 has no `vector` type. MariaDB 11.8 refuses a vector
components of large magnitude with error 1292 (1e30 and `math.MaxFloat32` are
refused; MariaDB does not document the threshold), and MySQL 9.7 takes the full
float32 range.
`types.Numeric` with a `precision` tag is `decimal(p,s)` (precision up to 65,
scale up to 30, scale not above precision; a precision alone is scale 0, and
`NaN` and infinity cannot be stored); without one it stays text, because a bare
DECIMAL would round. A string without `size:N` is text, and the generator
refuses text, blob and json in a primary key, unique key, index or foreign key
on MySQL and MariaDB, naming the column and asking for `size:N`. `types.Date` stays text, as its codec
stores it. `text` and `blob` hold 64 KiB, so use a `type` tag for more. Only an
error that wraps `momo.ErrUnsupported` shows as `unsupported`; any other error
from the type map fails the generation of this table.

The PostgreSQL type of `time.Time` can be changed for the whole project with the
`types:` section of `momo.yaml`, for example `types: {time.Time: timestamp(3)}`
for a database created by Prisma (see `naming: prisma` in ai-guide.md). Only
`time.Time` can be overridden; a `type:` tag on a field still wins, and SQLite
ignores the setting. `timestamp(3)` stores a wall clock without a zone, so
follow the `timestamp` notes below and pass UTC times.

On SQLite, `bool` is stored as 0 or 1, and `time.Time`, `types.UUID`,
`types.Date`, `types.Numeric` and `types.JSON[T]` are stored as text. The SQLite column is what
the generator emits. The SQLite driver (`driver/sqlitedriver`, cgo, not on
Windows) reads text columns back into `time.Time`, `*time.Time`,
`sql.NullTime`, `sql.Null[time.Time]` and `types.Date`, whatever the column was
declared as.

## Codec-provided mappings

These types are not in the generator's table. Their own `SQLType` method names
the column; the generator's table is the fallback for everything else.

| Go type           | PostgreSQL | SQLite |

| `types.TimeOfDay` | `time`     | `TEXT` |
| `types.Hstore`    | `hstore`   | `TEXT` |
| `types.TSVector`  | `tsvector` | `TEXT` |
| `types.TSQuery`   | `tsquery`  | `TEXT` |

`types.Hstore` needs the `hstore` extension; the vector types need `vector`
(pgvector). Momo never runs `CREATE EXTENSION` for you.

## Mappings you declare yourself

The generator never emits these columns, but the Go types work against them
when you write the DDL (or a migration) by hand. There is no SQLite column to
document because nothing generates one.

| Go type                 | PostgreSQL  | SQLite |
| ----------------------- | ----------- | ------ |
| `time.Time (timestamp)` | `timestamp` | `n/a`  |
| `string (decimal)`      | `numeric`   | `n/a`  |

## Range types

`types.Range[T]` is a PostgreSQL range column, with an empty range, infinite
bounds and inclusive or exclusive bounds. The element type `T` picks the range
type:

- `int32` is `int4range` and `int64` is `int8range`;
- `types.Numeric` is `numrange` and `types.Date` is `daterange`;
- `time.Time` is `tstzrange`, a range of timestamps with a time zone;
- `types.Timestamp` is `tsrange`, a range of timestamps without a zone. It is a
  struct around a `time.Time` whose wall clock is written without a zone and
  read back as a UTC time, the way the column stores it. It has
  `types.Timestamp.Infinity` and `types.Timestamp.NegInfinity` flags for the
  special timestamps, as `types.Date` has.

A `types.Range` holds a lower and an upper `types.Bound`, each with a `Value`, an
`Inclusive` flag and an `Infinite` flag (no limit on that side), and an `Empty`
flag. Build one with `types.ClosedOpen(lower, upper)` (`[lower,upper)`, the usual
form for a period), `types.NewRange` with `types.Incl`, `types.Excl` and
`types.NoBound` for any other shape, or `types.EmptyRange`. A nullable column is
a `*types.Range[T]` field.

The zero value `types.Range[T]{}` is the empty range: it is written as `empty`,
not as `(0,0)`, so a field you never set does not change on a round trip. It
reads back with `Empty` set, which is the same range but not the same Go value,
so ask the range whether it is empty (the `types.Range` method of that name)
rather than comparing with `==` when either may be the zero value. A bound may also be the special value infinity, which is not an
unbounded side: a `daterange` and a `tsrange` hold it in the element's
`types.Date.Infinity` and `types.Date.NegInfinity` flags (and the same flags of
`types.Timestamp`), while a `time.Time` cannot, so a `tstzrange`
whose bound is infinity fails to scan into `types.Range[time.Time]`. Use
`types.NoBound` for a `tstzrange` with no limit.

A range travels as the text PostgreSQL prints, such as `[1,10)`, `(,5]` or
`empty`: `Value` writes it and `Scan` reads it, so it needs no driver codec and
works with every driver the generator supports. The pgx driver turns its binary
form into that text before it reaches `Scan`. PostgreSQL stores `int4range`,
`int8range` and `daterange` in the canonical form `[lower,upper)`, so a range
written `(0,9]` reads back as `[1,10)`: compare ranges of those types in that
form. A `numrange`, `tsrange` and `tstzrange` keep the bounds as written. A
timestamp bound has microsecond precision.

The `rangeop` package queries them: `rangeop.Contains` for an element,
`rangeop.ContainsRange`, `rangeop.ContainedBy`, `rangeop.Overlaps`,
`rangeop.Adjacent`, `rangeop.StrictlyLeft`, `rangeop.StrictlyRight`,
`rangeop.IsEmpty`, `rangeop.LowerInfinite`, `rangeop.UpperInfinite`, and
`rangeop.Lower` and `rangeop.Upper` for the bounds, which compare like any scalar
expression. Each binds its operand with a cast to the range or element type.

Range types exist on PostgreSQL alone. The generator reports a `types.Range`
field when the target dialect is SQLite, MySQL or MariaDB, and a `rangeop`
builder fails the build with `momo.ErrUnsupported` there. Multiranges
(`int4multirange` and the others) and a range over another element type have no
Go type; `generate --from-db` reports such a column as unmapped, and an
`introspect` types rule or a `type` tag declares it. A GiST exclusion
constraint over a range is declared with `Config.Exclude`; see
[migrations](migrations.md#exclusion-constraints).

## Edge values and behavior

Each statement below is asserted by a test against PostgreSQL, and the ones
about SQLite or MySQL and MariaDB by the SQLite and MySQL tests named at the
top. The generated SQLite column of every row is also round-tripped on a live
SQLite database, except `NaN`, which SQLite does not have (see Floats). The
MySQL column of every row that has one is round-tripped on MySQL 8.4, MySQL 9.7
and MariaDB 11.8 (`TestTypeMappingMySQL`), with the edge values the MySQL
column holds.

- Integers: `math.MaxInt64` and `math.MinInt64` round-trip through `bigint`;
  `int` is 64-bit and maps to `bigint`. A value that does not fit the column
  (an `int64` above `math.MaxInt16` into `smallint`) is a database error, not a
  silent truncation. `uint64` has no mapping and is rejected when bound if it
  exceeds `math.MaxInt64`.
- Floats: `NaN`, `+Inf` and `-Inf` are legal `double precision` and `real`
  values and round-trip. Compare with `math.IsNaN`, since `NaN != NaN`. SQLite
  has no `NaN`: binding a `float32` or `float64` `NaN` (or a pointer to one) is
  `ErrValidation` and nothing is stored, rather than a silent `NULL`. `+Inf` and
  `-Inf` are legal `REAL` values. MySQL and MariaDB have no `NaN` or infinity in
  `float` and `double`: binding one is a database error.
  A `float` column read by a query with no arguments comes back over the text
  protocol, where MySQL 8.4, MySQL 9.7 and MariaDB 11.8 print it with six
  significant digits (`math.MaxFloat32` reads back as `3.40282e+38`). A query
  with an argument uses the binary protocol and returns the exact `float32`, as
  does `CAST(col AS DOUBLE)` or `col + 0e0` in the select list. Use `double`
  (`float64`) for a column whose exact value matters on every read path.
- Strings: any valid UTF-8 round-trips, including quotes and backslashes (they
  are bound, never interpolated). PostgreSQL rejects U+0000 in `text`. A string
  longer than `size` is a database error on `character varying(N)`.
- `[]byte`: `nil` stores NULL; an empty non-nil slice stores an empty `bytea`.
- `time.Time` on `timestamptz`: the instant is preserved, the zone is not. A
  value written at `+05:30` reads back as the same instant in the server
  session's location, so compare with `Time.Equal`, not `==`. Precision is
  microseconds; finer digits are cut. Times before 1970 and year 9999 work.
- `time.Time` on `timestamp` (no zone): you store a wall clock. Pass
  `t.UTC()` and treat the column as UTC; a value in another zone is stored as
  its UTC wall clock.
- `types.Date`: stores the year, month and day of `Time` in its own location;
  it reads back at midnight UTC. Compare the date, not the zone. PostgreSQL
  `infinity` and `-infinity` round-trip through the Infinity and
  NegInfinity fields (`Time` is ignored while one is set, and zero after a
  read); `IsFinite` tells an ordinary date from a special one. SQLite and
  MySQL have no special dates: a `types.Date` with a flag set is
  `ErrValidation` and nothing is stored, also inside a `sql.Null`. Setting both
  flags is an error.
- `types.Numeric`: an exact decimal kept as text in `Decimal` (`"-12.50"`; empty
  is 0). PostgreSQL `numeric` returns what it stored, so a value beyond
  `float64` precision and its scale survive. `NaN`, Infinity and
  NegInfinity round-trip through their flags (set at most one, and leave
  `Decimal` empty); `IsFinite`, `IsNaN`, `IsInfinite` and `Sign` classify a
  value (`Sign` is 0 for `NaN`). Infinity and `-Infinity` need PostgreSQL 14
  or later (`NaN` is older); CI covers PostgreSQL 16 and 17.
  `types.ParseNumeric` reads PostgreSQL text and rejects an exponent or
  anything that is not a number. Scanning also takes an `int64` and a `float64`
  (what SQLite returns for an expression); it does not take a
  `pgtype.Numeric`.
- SQLite and MySQL have no `NaN` or infinity: binding one in a `types.Numeric`
  (also inside a `sql.Null`) is `ErrValidation`, as for a float `NaN` on SQLite.
  The column is `TEXT` there, so the database does not order or add it as a
  number, and a `precision` or `scale` tag still generates `TEXT`, not
  `numeric(p,s)`: SQLite would give that NUMERIC affinity and turn `12.50` into
  `12.5`. On PostgreSQL the tags generate `numeric(p,s)`.
  On PostgreSQL the `sqlfn` arithmetic helpers (`sqlfn.Add`, `sqlfn.Sub`, `sqlfn.Mul`, `sqlfn.Div`
  and their `Expr` forms) and `sqlfn.NullIf` accept a `types.Numeric`, and the
  database does the exact arithmetic; on SQLite and MySQL they fail with
  `ErrUnsupported`, because the column is `TEXT` there and `+` would go through
  floating point. `types.NumericFromInt64` and `types.NumericFromFloat64` build
  a value from a Go number (a `float64` is already binary: `0.1` gives `"0.1"`,
  its shortest decimal, and NaN or an infinity is an error). Momo does no
  other arithmetic on a `types.Numeric`.

  ```text
  // agent_conversation.cost numeric(12,6), momo.Column[types.Numeric]
  cost, err := types.NumericFromFloat64(0.000412)
  if err != nil { return err }
  agentconversation.Cost.SetExpr(sqlfn.Add(agentconversation.Cost, cost))
  // roughly: SET cost = (agent_conversation.cost + $1), exact in numeric
  ```

- `types.UUID`: round-trips all 16 bytes, including the all-zero UUID.
- `types.JSON[T]`: encodes with `encoding/json`. An empty slice and a nil
  slice are different JSON (`[]` and `null`) and read back as such.
  Query it with `jsonop.Text`, `jsonop.Path`, `jsonop.Root` (a scalar at the
  root), `jsonop.Contains` and `jsonop.HasKey`, and compute with
  `jsonop.DeleteKey`, `jsonop.Concat` and `jsonop.Set` (package
  `github.com/azrtydxb/momo/jsonop`; `jsonop.Concat` and `jsonop.Set` are
  PostgreSQL only and need `jsonb`). A
  nullable column holds either SQL NULL or the JSON literal null; an extraction
  is NULL for both and for a missing key, so test the column itself with
  `IsNull`.

  Reading keeps the two apart when you scan into a `*types.JSON[T]` field (a
  nullable column): SQL NULL gives a nil pointer, and the JSON literal null
  gives a non-nil pointer whose `IsNull` method returns true. Writing it back
  stores the JSON literal null, not SQL NULL; a nil pointer stores SQL NULL.
  `types.JSONNull` builds a JSON null value to write. This holds on PostgreSQL
  (`jsonb`, native and `FromSQLDB` drivers), SQLite and MySQL, where the column
  is `TEXT` and any stored text that is `null` (white space around it ignored)
  counts as the JSON null. A plain, non-pointer `types.JSON[T]` field still
  errors on SQL NULL and reads the JSON null as the zero `T` with `IsNull`
  true.

  `IsNull` stays true after a read while `V` is the zero value of `T` or still
  encodes as `null` (a `json.RawMessage` holding `null`, the generated default
  type, or a `T` with its own `UnmarshalJSON`). To give a value read as null
  new contents, assign through `types.JSON.Set` or a fresh `types.JSON[T]{V: v}`.
  Assigning `V` directly to its zero value (`false`, `0`, `""`) keeps the JSON
  null, because the zero value cannot be told from an untouched `V`.

  `types.JSON[T]` has a private field and no `MarshalJSON`. Two values compare
  equal with `==` only when the null state matches, so a scanned null differs
  from `types.JSON[T]{}`; go-cmp needs a comparison option that ignores the null state.
  `encoding/json` renders any `types.JSON[T]` as `{"V":...}`, and
  `types.JSONNull[T]()` as `{"V":null}`: the null state does not survive an API
  round trip through `encoding/json`.

  Grouping by an extraction works only for plain keys (letters, digits,
  underscore) and not on a sensitive column; see the AI guide pitfalls.

- `types.TimeOfDay`: nanoseconds since midnight, truncated to microseconds
  (PostgreSQL `time` precision); `86399999999000` is the last representable
  value, and a value outside one day is an error.
- `types.Hstore`: a nil `*string` value is an hstore NULL; keys and values
  with quotes and backslashes are escaped.
- `types.TSVector` and `types.TSQuery`: the server's text form, with the
  lexemes sorted and normalized, so write values in that canonical form to
  compare them with `==`. An empty tsvector reads back empty. Full-text
  expressions are PostgreSQL only (see docs/fulltext.md).
- `[]string` on `text[]`: elements containing commas, quotes, the text `NULL`,
  or empty strings round-trip; an empty slice reads back empty.
- Slices as arrays: only `[]string`, `[]int16`, `[]int32`, `[]int64`, `[]bool`,
  `[]float32`, `[]float64` and `[]types.UUID` (`uuid[]`) map, and so does a `[]uuid.UUID` from
  github.com/google/uuid (see the next item). `[]int` is not mapped, because its width is
  platform dependent; use `[]int64`. `[]string` with a `size` tag becomes
  `character varying(N)[]`. A nil slice binds as NULL, so inserting it into a
  `NOT NULL` array column fails with a not-null violation; pass an empty
  non-nil slice (it stores `{}`), or give the column a `default '{}'` and omit
  it. The array predicates bind a nil value list as an empty array, never NULL.
- `uuid.UUID`, `*uuid.UUID` and `[]uuid.UUID` from github.com/google/uuid map to
  `uuid` and `uuid[]` on PostgreSQL and `uuid.UUID` to `TEXT` on SQLite (canonical
  text; `[]uuid.UUID` has no SQLite column), with no `type:` tag. MySQL has no
  uuid mapping, as for `types.UUID`. The generator recognizes the type by its
  import path and adds no dependency to momo; your module requires
  github.com/google/uuid only when your models import it. `--from-db` writes
  these types with `introspect.uuid: google`. A named type over `uuid.UUID`
  (`type ID uuid.UUID`) is not mapped: give the field `type:uuid`. A UUID type
  of another package is not mapped either.
- Decimal: carry `numeric` as `types.Numeric` (exact, with `NaN` and the
  infinities), or as a string to avoid binary floating point. Values beyond
  `float64` precision round-trip exactly, and `numeric` also accepts `NaN`.

## Reading a SQLite database with --from-db

`momo generate --from-db` on a SQLite database maps a declared column type to a
Go type by the type affinity rules of SQLite, the inverse of the SQLite column
of the generated mappings above. It adds a `type:` tag with the declared type
whenever the Go type's own SQLite column differs, so the models build the column
back as it was.

- A name with `INT` (`INTEGER`, `BIGINT`) is `int64`.
- A name with `CHAR`, `CLOB` or `TEXT` is `string`.
- A name with `BLOB` is `[]byte`.
- A name with `REAL`, `FLOA` or `DOUB` is `float64`.
- `BOOLEAN` is `bool`; `DATETIME` and `TIMESTAMP` are `time.Time`; `DATE` is
  `types.Date`; `NUMERIC` is `float64`, with a report note.

The `type:` tag carries the declared type unless the Go type's own SQLite
column already spells it that way (`INTEGER`, `TEXT`, `BLOB`, `REAL`).

`NUMERIC` is mapped, with a note, because a bare `NUMERIC` column converts
well-formed text to an integer or a real and `float64` reads either; a
`DECIMAL(10,2)` column is not, because its declared precision says the values
are exact decimals that `float64` would round, so a rule must choose
`types.Numeric` or a decimal type. `BOOLEAN`, `DATETIME`, `TIMESTAMP` and `DATE`
columns get a report note too: SQLite keeps what was written, so a value other
than 0 or 1, a unix-timestamp integer or text that is not a date fails to scan
into `bool`, `time.Time` or `types.Date`.

Any other declared type has NUMERIC affinity, which holds integers, floats and
text alike, so it has no single Go type: `DECIMAL(10,2)`, a `json` column and a column
with no declared type are errors until an `introspect.types` or
`introspect.columns` rule names the Go type. The column text is never guessed.

## Null handling

A column that can be NULL needs a Go type that can hold NULL: a pointer
(`*int64`), a `sql.Null*` wrapper, or a type whose `Scan` accepts nil.
Scanning NULL into a plain `int64` or into a codec from the `types` package is
an error, never a silent zero value.

## Models from a MySQL database

`momo generate --from-db` on MySQL and MariaDB writes the exact column type in
a `type:` tag, so the generator's own MySQL column is not needed for a model it
wrote. The Go type chosen for each MySQL type is in
[MySQL and MariaDB](mysql.md#models-from-a-database): unsigned integers are
`uint8` to `uint64`, `tinyint(1)` is `bool`, `decimal` is `types.Numeric`,
and `enum` and `set` are `string`. `tinyint(1)` is `bool`, and MySQL lets that
column hold any value from -128 to 127: a stored value other than 0 or 1 fails
to scan the whole row. Every such column gets a note in the report; map
`tinyint(1)` to `int8` with an `introspect.types` rule if it holds other values.
