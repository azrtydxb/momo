## 1. Model

```text
models (Go structs) --momo migrate diff--> <v>_<name>.up.sql + <v>_<name>.snapshot.json + momo.sum
                                              |
database <--------momo migrate apply---------+  (history table: momo_migrations)
```

### Files

All files live in one directory per dialect (default `migrations/postgres`,
set `migrate.dir.postgres` or `--dir`). `diff` writes exactly three files:

| File                             | Content                                                                                                                                                                        |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `<version>_<name>.up.sql`        | Statements. Header `-- momo:generated`, plus `-- momo:destructive` and/or `-- momo:no-transaction` when needed. Statements are separated by a blank line and each ends in `;`. |
| `<version>_<name>.snapshot.json` | The whole schema after this migration, wrapped as `{format_version, version, parent, schema}`. `schema` carries its own `format_version`.                                      |
| `momo.sum`                       | Checksum manifest of every file in the directory, rewritten by `diff`.                                                                                                         |

- `version` is a 14-digit UTC timestamp (`YYYYMMDDHHMMSS`). If the clock is not
  past the latest existing version, `diff` uses the second after it, so
  versions only grow.
- `name` must match `^[a-z][a-z0-9_]*$`.
- `.down.sql` files are optional and hand-written (`diff` never generates one).
  They are hashed in `momo.sum`, and `apply` never runs them. Only
  `Engine.Rollback` runs them (section 2).
- Files whose name starts with `.` are ignored everywhere (`.DS_Store`,
  `.momo-*.tmp`). A symlink to a directory inside the migration directory is an
  error. Moving an applied file into a subdirectory is fine: history is keyed by
  version, not path (`TestMovingAppliedMigrationIntoArchiveKeepsHistory`).
- `diff` never overwrites a file (exit 1 if one exists) and writes all-or-none:
  temporaries first, then publish, `momo.sum` last.

### Diff

`momo migrate diff <name>` runs offline (no database, no driver). It loads the
models, compares them with the snapshot of the highest version in the
directory (the empty schema when there is none), orders the changes by
dependency and renders SQL. No difference: prints `no changes`, exit 0, writes
nothing.

- Renames are never guessed. A drop plus an add prints a
  `hint: possible rename ...`; pass `--rename-table old=new` or
  `--rename-column table.old=new`.
- Dropped extensions and schemas are not dropped in the database; `diff` prints
  a hint that they are no longer managed.
- Diff never reads the database. A table that is already populated is
  indistinguishable from an empty one (see section 5).

`diff` does not depend on `momo generate`. `momo generate --check` verifies only
the generated `*_gen.go` files (exit 1 and `stale: <path>` lines when stale).
There is no `momo migrate diff --check`. To fail CI when the models have no
migration, run `momo migrate diff ci_probe` on a clean checkout and fail unless
it prints `no changes` (when there is a difference it writes files and exits 0,
so also check `git status --porcelain` on the migration directory). This recipe
is derived from the code, not covered by a test.

### Checksums

Two independent checks, both SHA-256 of the file bytes:

1. `momo.sum` must match the directory: every file present, none added,
   removed or changed. `Engine.Apply`, `Status` and `Baseline` refuse otherwise
   (`ErrChecksumMismatch`, naming the files). A missing `momo.sum` is an error
   that names `momo migrate hash`. `momo.sum` itself carries a directory hash;
   a hand-edited `momo.sum` is rejected.
2. The history row of an applied migration stores the checksum of its up file.
   `Engine.Apply` refuses when that file changed since (the error says
   `... changed after version V was applied`).

`Plan` and `Drift` do not check either.

### History table

`momo_migrations`. Every statement against it (read, insert, update, delete
and the `CREATE TABLE`) names the table schema-qualified and quoted, for
example `"app"."momo_migrations"`. The table is resolved before the lock is
taken, and again right after, and the advisory-lock key is built from that
resolved schema, so a migration that changes `search_path` cannot redirect the
history writes. If the two lookups disagree (another process created the table
in an earlier schema in between), the lock is released and the attempt is
repeated once; a second disagreement fails with an error asking you to retry.

- An existing table is found the way earlier versions found it, through the
  session `search_path`, and its schema is then used. Installs made with the
  unqualified name keep working, and no second table is created.
- The resolved object must be a regular, permanent table, and the connecting
  role must be its owner or hold the privileges of the owning role
  (`pg_has_role` with `USAGE`, so a role with NOINHERIT does not qualify). A
  superuser holds every role's privileges, so a superuser migrator
  additionally requires the owner to be itself or another superuser; a table
  owned by an ordinary role is refused, because its triggers and rules would
  run with superuser rights. A view, foreign table, unlogged or temporary table, or a table
  owned by an unrelated role, named `momo_migrations` earlier on the
  `search_path`, is refused with a validation error naming the schema, the
  table and the owner; it is never used. A table adopted on first install by
  `CREATE TABLE IF NOT EXISTS` passes the same checks after the statement runs.
- What this does and does not defend: it stops a foreign-owned or non-table
  object that sits ahead of the real table on the `search_path` from
  capturing the history writes. It does not stop a role whose privileges you hold,
  or another superuser, from owning such an object, and it cannot protect a schema
  that other roles may write to and that is ahead of yours on the
  `search_path` before any table exists. Keep schemas on the migrator's
  `search_path` writable only by the migrator.
- With no table yet, it is created in the current schema.
  `migrate.Config.Schemas[0]` (`migrate.schemas`) must equal the current schema
  (current_schema) or the engine returns a configuration error naming both.
  `plan`, `status` and `drift` on a connection with no current schema and no
  table report an empty history; `apply` and the other writers fail.
- momo does not `SET search_path` for the migration session. Migrations are
  written against the `search_path` of the connection you give momo and may
  rely on it; qualify the history table, not the migrations. Set the
  `search_path` in the connection URL, and pin it per role with
  `ALTER ROLE` on the migrator role.

| Column               | Type             | Meaning                                                                                   |
| -------------------- | ---------------- | ----------------------------------------------------------------------------------------- |
| `version`            | TEXT PRIMARY KEY | Migration version                                                                         |
| `name`               | TEXT             | Migration name                                                                            |
| `checksum`           | TEXT             | SHA-256 of the up file                                                                    |
| `status`             | TEXT             | `running`, `applied`, `failed`, `rolled_back` (and `meta`)                                |
| `statements_applied` | INTEGER          | Statements that completed                                                                 |
| `error`              | TEXT             | Failure text, empty on success                                                            |
| `applied_at`         | TEXT             | RFC 3339 UTC                                                                              |
| `execution_ms`       | BIGINT           | Duration                                                                                  |
| `apply_id`           | TEXT             | UTC timestamp plus 8 hex digits, shared by one `apply` run; `baseline` for baselined rows |
| `kind`               | TEXT             | `sql` (default), or `go` for a Go migration (section 6a)                                  |

One extra row, `version = '__momo_meta__'`, `status = 'meta'`, holds the
history format version. `ReadHistory` and `Inspect` hide it and the table.
`running` and `failed` are "dirty". `rolled_back` is not dirty.

### How apply decides what to run

1. Take the migration lock, set session timeouts, create the history table if
   missing.
2. Refuse (`ErrDirty`, exit 3) if any row is `running` or `failed`.
3. Refuse (`ErrChecksumMismatch`, exit 3) on a checksum problem (above).
4. Pending = every `*.up.sql` and every registered Go migration (section 6a)
   whose version has no row other than
   `rolled_back`, run in ascending version order, optionally stopping after
   `--to N` (a version without a file is refused, so a typo applies nothing).

The test is "has no row", not "is newer than the latest applied". An older file
that appears later (a merged branch) is still applied, after newer ones.
`apply` does not check snapshot parents; `validate` does (section 2).

### Drift

`momo migrate drift` inspects the live database and compares it with the
snapshot of the **latest applied** migration (the empty schema if none, so
every object is unmanaged). Exit 0 and `no drift`, or exit 1 and one line per
finding:

| Line                               | Meaning                                                                                                                                                                                                                   |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `changed: <kind> <name>: <detail>` | In both, definition differs. A column, index or constraint present only live is `changed: ... not in snapshot` on that object. An invalid index is `changed: ... invalid index (failed CONCURRENTLY build)`.              |
| `missing: <kind> <name>`           | In the snapshot, not in the database.                                                                                                                                                                                     |
| `unmanaged: <kind> <name>`         | In the database, not in the snapshot: tables, views, functions, enums, schemas, **extensions** (every extension except `plpgsql`, for example `pg_stat_statements`, `pgcrypto`), and triggers/policies on managed tables. |
| `unverified: <kind> <name>`        | Not compared and does not affect the exit code (below).                                                                                                                                                                   |

- Extension versions are ignored when either side leaves the version empty.
- Hide objects you do not manage with `migrate.exclude` (globs over `name` or
  `schema.name`; they apply to tables, views, functions, enums, extensions,
  triggers and policies). Example: `exclude: ["pg_stat_statements", "audit_*"]`.
  PostgreSQL inspection applies the globs while it reads, before an object is
  examined: a matching table is skipped before its columns, constraints, indexes
  and partitions are read, a matching view or function before its definition is
  read, and a trigger whose own name or table matches before its definition is
  read. So an object the schema model cannot represent (for example a table with
  a `VIRTUAL` generated column) no longer fails `generate --from-db`, `baseline`
  or `drift` once you exclude it. Extensions, enums and policies are not skipped
  early; they are filtered afterwards as before. `generate --from-db` also
  passes every `introspect.skip` glob to inspection the same way, so a skipped
  table is never read (the globs also match views and functions of that name).
- A trigger limited to some columns (`AFTER UPDATE OF state`) is
  `schema.Trigger.UpdateOf`: PostgreSQL renders `UPDATE OF "state"`, inspection
  reads the list back and `generate --from-db` writes it into the model.
- `momo_migrations` is never reported.
- A view query, trigger `WHEN` and policy `USING`/`WITH CHECK` changed outside
  migrations is reported as `changed:` (the detail names `query`, `when`,
  `using` or `check`), and a body declared in another spelling than the server
  reports (`id>0` against `id > 0`) is not drift. To compare them, drift
  rewrites the snapshot's text through a scratch schema in a rolled-back
  transaction (the same step as `baseline`), which needs **`CREATE` on the
  database** and a writable session. No DDL runs against the application
  schema (`TestDriftBodiesRunsDDLOnlyInRolledBackTransaction`).
- A role that cannot do that (a read-only CI role, say) still gets a report:
  the bodies are listed as `unverified: <kind> <name>` and do not affect the
  exit code, so exit 0 does not prove they match. `momo migrate drift --strict`
  (`Engine.DriftWith(ctx, DriftOptions{Strict: true})`) turns that case into an
  error: exit 3 with a message wrapping `ErrCanonicalizePrivilege` that names
  the privilege. Use `--strict` where a clean report must mean the policies
  were checked, since a policy loosened to `USING (true)` hides in `unverified:`
  otherwise (`TestDriftBodiesNeedCreateOnDatabase`, both modes, as `momo_app`).
  Function bodies are compared in both modes.
- A snapshot without those bodies canonicalizes only its table text (defaults,
  checks, index predicates) through the same scratch schema. There drift stays
  tolerant: without `CREATE` it still runs and can show false `changed` entries
  (never hides a real one), and lists the tables it compared as declared in
  `CanonicalizeSkipped`.

`validate` checks: files parse and directives are known; `momo.sum` matches;
versions unique and increasing; each snapshot's parent exists; no two snapshots
share a parent (branch conflict); each up file has a snapshot; a hand-written
migration (no `-- momo:generated`) has a snapshot equal to its parent's. Use it
in CI. `apply` runs the chain checks too (fork, missing parent, cycle, gap) and
refuses with the same message (a fork is `ErrBranchConflict`; a missing parent,
cycle or gap is `ErrChainInvalid`; both exit 1, like `validate` findings), and it
refuses with `ErrOutOfOrder` (exit 1) when a pending version is older than the
latest applied one, so a late-merged older migration is never applied after newer
ones (`TestApplyRefusesForkedChain`, `TestApplyRefusesPendingOlderThanApplied`,
`TestApplyRefusesBrokenChain`, `TestMigrateChainRefusalsExitOne`).

Recovering from `ErrBranchConflict` or `ErrOutOfOrder`. Both mean two teammates branched from the same snapshot and both
merged: two snapshots share a parent, and one of the new migrations has a
version older than the other. Fix it in the files of the branch that merged
last, before it is applied anywhere. The late migration is still pending, so it
needs no `rehash`:

With a checkout of the target branch's migration directory (Momo has no git
dependency, so make it with `git archive` or a second checkout),
`momo migrate rebase --onto <dir> [name]` does steps 1 and 2 below in one
command and validates the result. It refuses, naming the file, a branch
migration without `-- momo:generated` or with a hand-written `.down.sql`, and a
target directory that is not a valid chain. `--onto` takes a directory only. The
branch directory must hold every migration of the target, as after a merge;
the command prints `problem:` lines and exits 1 when it does not. By hand:

1. Delete its `<version>_<name>.up.sql` and `<version>_<name>.snapshot.json`
   (a generated migration; for a hand-written one rename the `.up.sql` to a
   version later than the newest applied one and copy the newest snapshot to
   the same new version, with `parent` set to the previous snapshot).
2. Run `momo migrate diff <name>`. It compares the models with the latest
   snapshot and writes the migration again with a new version and the right
   parent.
3. Run `momo migrate hash`, review the `changed:/added:/removed:` list, and run
   `momo migrate validate`.

If the older migration was already applied somewhere, do not rewrite it: leave
the chain as it is and add a new migration for the difference.

`momo migrate new --custom <name>` writes an empty hand-written migration
(section 6).

- `momo migrate rollback [--group]` (`Engine.Rollback(ctx, RollbackOptions{Group: false})`) runs the `.down.sql` of
  the last applied migration (the applied row with the greatest `applied_at`);
  with `Group: true` it runs the downs of every row that shares the greatest
  `apply_id`, in descending version order. It takes the same lock and session
  timeouts as `Engine.Apply`, refuses a dirty database or a checksum mismatch, and
  returns `ErrNoDown` before running anything when any selected version has no
  down file. A transactional down runs in one transaction together with the
  history update; the row becomes `rolled_back`, so the version is pending
  again and the next `apply` runs it anew. A down with `-- momo:no-transaction`
  runs statement by statement and, if one fails, leaves the row `failed`
  (dirty, settle it with `resolve`). A rollback undoes schema, not data: write
  the down so that it can run on a populated table (`TestRollbackGroup`,
  `TestRollbackNoDown`).
- `momo migrate rebase` (`Engine.Rebase(ctx, target, desired, name)`) takes the directory of the target
  branch (from `git`, Momo has no git dependency). It lists every file of the
  branch's migrations that the target lacks, refuses with the file name when one
  has no `-- momo:generated` header, and regenerates one migration on top of
  the target's latest snapshot. It first validates the target (momo.sum, chain,
  snapshots) and refuses a broken one, and it refuses a branch migration that
  has a hand-written `.down.sql`, naming the file. It writes nothing: the
  caller deletes the returned files and writes the new ones, which the command
  does (`TestMigrateRebase`).

There is no `--force-unlock`: the PostgreSQL lock is a session advisory lock that
the server frees when its holder's connection ends (section 3). `--lock-wait`
exists on `apply` only.
`--lock-wait 0s` fails immediately when locked. `resolve` and `baseline` wait
the default 30 s.

Database URL: `--url`, else the variable named in `migrate.url_env.postgres`,
else `MOMO_DATABASE_URL`. Prefer the environment, or `--url -`, which reads the
URL from standard input (`printf '%s' "$URL" | momo migrate apply --url -`): a
`--url` value shows in the process list of a shared host, and momo prints a
warning on stderr when it sees one.

`momo.yaml` `migrate:` keys: `dir`, `url_env` (maps keyed by dialect),
`schemas`, `lock_timeout`, `statement_timeout` (Go durations), `exclude`,
`external_extensions` (section 7).

## 3. Apply semantics on PostgreSQL

One connection is pinned for the whole run. Order: lock, set timeouts, history
table, migrations, reset timeouts, unlock (reset runs first so a small
`statement_timeout` cannot cancel the unlock). Cleanup runs on a
context detached from Ctrl-C and has two steps: the two RESETs share one 5 s
bound, and the unlock has its own.

### Lock

`pg_try_advisory_lock(id)` on the pinned session, polled every 200 ms until
`--lock-wait` (default 30 s) passes. `id` = FNV-64a of
`momo:<schema>.momo_migrations`, where `<schema>` is the schema of the resolved
history table (the current schema when none exists yet), so schemas are
independent. On timeout
`apply` exits 3 with
`migration lock is held by another process: held by pid=N application_name=X`
(`TestApplyLockWaitTimesOutWithHolder`; waiting
callers proceed once it is released, `TestApplyWaitsForLockRelease`).

The lock is session-scoped: it is released when the holder's connection ends,
so a crashed process frees it. There is no lock row to delete and no flag to force
the lock (`--force-unlock` was removed: it never did anything). If a lock appears stuck, find the session
(`pg_stat_activity` by the pid in the message) and terminate it with
`pg_terminate_backend`.

`apply`, `resolve` and `baseline` take the lock. `plan`, `status`, `drift`,
`validate` do not.

### Transactions

- **Default: one transaction per migration file**, not per batch. The
  `running` history row, all statements and the update to `applied` commit
  together. A second migration failing never undoes a first that committed.
- **Marked `-- momo:no-transaction`: the whole file runs with no
  transaction**, one autocommitted statement at a time, with `statements_applied`
  updated after each. Every statement in that file loses atomicity, not only
  the concurrent one. Only the directive selects this mode on apply; `apply`
  does not inspect statements. `diff` writes the directive when it renders a
  concurrent index. A hand-written file must carry the directive itself:
  otherwise PostgreSQL rejects `CREATE INDEX CONCURRENTLY` inside a
  transaction, the version is recorded `rolled_back`, and it can be retried
  after you add the directive. `diff` never mixes the two modes in one file:
  when a diff holds both transactional DDL and statements that must run outside
  a transaction, it writes two migrations, the transactional one first and a
  trailing `<name>_no_tx` one that carries the directive (one second later
  version). A failure in the first file rolls it back whole. A diff with only
  such statements writes the single no-transaction file.
- Statements run one by one with no bind parameters. The splitter respects
  strings, comments and `$$` bodies; `-- momo:split` disables dollar-quote
  awareness and splits at every semicolon.

`CREATE INDEX CONCURRENTLY` applies correctly when it is in a no-transaction
file: the index is valid and the version is `applied`
(`TestCreateIndexConcurrentlyApply`). `diff` produces it from `Concurrently()`
on a model index, and for `ADD UNIQUE` and the `VALIDATE CONSTRAINT` of an
`ADD CHECK` (section 5).

### Session timeouts

Applied with `SET` on the pinned session, `RESET` at the end:

| Setting             | momo.yaml                   | Default | Notes                                                                                                                                                                                                                                                                                                         |
| ------------------- | --------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lock_timeout`      | `migrate.lock_timeout`      | 5 s     | A DDL statement that cannot get its table lock within the limit fails with SQLSTATE 55P03; the transaction rolls back and the version stays retryable. Key absent: 5 s. `0s` sets `lock_timeout = 0`, which disables the limit.                                                                               |
| `statement_timeout` | `migrate.statement_timeout` | not set | Left as the role or server default. A role-level `statement_timeout` therefore applies to long migrations such as index builds. Use a migration role without it. Key absent: untouched. `0s` sends `SET statement_timeout = 0`, which disables the limit even when the role has one (for a long index build). |

If `RESET` fails, the connection is discarded rather than returned to the pool.

### PgBouncer and other poolers

Run migrations on a direct connection or a session-pooled one. Under
transaction pooling the advisory lock, the `SET lock_timeout` and the
`search_path` belong to a server connection that the next statement may not
reuse, so the lock does not protect and the timeouts can leak or not apply.
The driver's default query mode is PgBouncer-safe for application queries; the
migration engine through PgBouncer is **not tested** in v0.6.0. A startup <!-- x-release-please-version -->
`search_path` is also not reliable through a pooler, so set the schema on the
role or on a direct connection.

## 3a. SQLite

`migrate/sqlite` is the SQLite migration dialect. It is a library API: pass it
to the engine with `migrate.WithDialect(sqlite.New())` and a
`driver/sqlitedriver` driver (cgo, not Windows). The `momo migrate` command does
not select it yet, so there is no `--dialect sqlite`. The tests that pin the
behavior below run on a real SQLite in the integration suite
(`TestSQLiteInspectRoundTrip`, `TestSQLiteAlterDecision`,
`TestSQLiteRebuild`, `TestSQLiteLockTable`, `TestSQLiteEngineLifecycle`,
`TestSQLiteRenderApplyInspectDiffIsZero`).

**Inspection.** Tables, columns (type, NOT NULL, default, collation, generated
expression), the primary key, UNIQUE constraints, indexes (including expression
and partial indexes), foreign keys, CHECK constraints, views and triggers. The
`momo_migrations` and `momo_migration_lock` tables, the `sqlite_` tables,
virtual tables and the shadow tables of virtual tables are left out. An
`INTEGER PRIMARY KEY` of a rowid table is reported with identity `by_default`,
and the schema normalizer gives that column the same identity on the model side,
so the two compare equal. A trigger is its `CREATE TRIGGER` text
(`schema.Trigger.Definition`), compared after whitespace and case outside quotes are
normalized. Extensions, native enums, functions, policies, partitions,
row-level security and schemas do not exist on SQLite and are never reported.

**Enums.** SQLite has no enum type. A TEXT column that carries
`CHECK ("col" IN ('a', 'b'))` is inspected as an enum column whose enum is named
`<table>_<column>`, and `Engine.Diff` writes an enum column back as that CHECK.
A model enum therefore round-trips without a diff only when it is named
`<table>_<column>`. `create_enum` and `drop_enum` produce no statement;
`alter_enum_add_value` rebuilds the tables that use the enum.

**ALTER or rebuild.** SQLite changes a table in place only for these:
`ALTER TABLE ... RENAME TO`, `RENAME COLUMN`, `ADD COLUMN`, `DROP COLUMN`, and
index, view and trigger statements. The renderer uses them when the
[restrictions in the SQLite documentation](https://www.sqlite.org/lang_altertable.html)
allow it: an added column must not be PRIMARY KEY, UNIQUE, a stored generated
column, an enum or identity column, or NOT NULL without a non-NULL default, and
its default must not be `CURRENT_TIMESTAMP` (or `CURRENT_DATE`, `CURRENT_TIME`)
or a parenthesised expression; a dropped column must not be in the primary key,
a UNIQUE constraint, an index (key or `WHERE`), a CHECK, a foreign key (either
side), a generated column's expression, a trigger or a view. Everything else
(`alter_column`, any primary key, unique, check or foreign key change, and an
add or drop of a column that breaks a restriction) rebuilds the table, and all
changes to that table in the same diff become one rebuild.

**The rebuild** follows
[the 12 steps in the SQLite documentation](https://www.sqlite.org/lang_altertable.html#otheralter).
`diff` writes them as plain statements into the up file and puts
`-- momo:sqlite-foreign-keys-off` at the top of the file. On `apply` the engine
runs `PRAGMA foreign_keys = OFF` outside the transaction (the pragma does
nothing inside one), runs the file in one transaction and turns enforcement back
on afterwards, also when the migration failed. The statements are: drop every
view and trigger that mentions the table (directly or through another view),
`CREATE TABLE "new_<table>"`, `INSERT ... SELECT` of the columns the old and new
table share, `DROP TABLE`, `RENAME`, `CREATE INDEX` for each index, recreate the
dropped views and triggers that the desired schema keeps unchanged, and
`PRAGMA foreign_key_check`. If that pragma returns a row the statement fails
with `momo.ErrForeignKeyViolation` naming the table and row, and the transaction
rolls back (`TestSQLiteRebuildOrphanRollsBack`). Row count and content, indexes,
triggers and views survive (`TestSQLiteRebuild`, `TestSQLiteRebuildKeepsDataAndObjects`)
and foreign keys are enforced again afterwards (`TestSQLiteRebuildFKStillEnforced`).

Limits of the rebuild:

- After each recreated view the file runs `SELECT 1 FROM "view" LIMIT 0`,
  because `CREATE VIEW` does not check the names in its query. A view that names
  a dropped column therefore fails the migration. `sqlite.Rebuild` with
  `migrate.RunStatements` reports that as `migrate.ErrRebuildBlocked` naming the
  view; a migration read back from a file has lost the statement hints, so the
  engine reports the failing statement number instead.
- A trigger body is resolved only when the trigger fires, so a trigger that names
  a dropped column is recreated and fails later.
- A table can be rebuilt only if it has columns in common with the new
  definition; `INSERT` is skipped otherwise.
- `sqlite.Rebuild` and `sqlite.Capture` rebuild from a live connection
  (captured views and triggers are recreated verbatim); the engine path rebuilds
  from the snapshot instead.
- A model cannot declare `WITHOUT ROWID`, `STRICT` or `AUTOINCREMENT`, so a
  table that has one in the database and not in the model is not a difference:
  `diff` and `AutoMigrate` leave it alone and a rebuild writes it back
  (`TestSQLiteAutoMigrateWithStrictTable`). Asking for one the table lacks is
  refused by `diff` (write a custom migration). `schema.Table` carries `Strict`
  and `Autoincrement`; inspection reads them. A rebuild of an `AUTOINCREMENT`
  table copies its `sqlite_sequence` value to the new table, so ids of deleted
  rows are not handed out again (`TestSQLiteStrictAutoincrementRoundTrip`).
  An `INTEGER PRIMARY KEY DESC` is not a rowid alias and is not reported as an
  identity.
- A down migration that rebuilds a table carries the same
  `-- momo:sqlite-foreign-keys-off` line; `Rollback` honours it as `apply` does
  (`TestSQLiteRollbackRebuildKeepsChildRows`).

**Unsupported.** These fail with an error that wraps `momo.ErrUnsupported`
instead of being dropped: `create_schema`, `create_extension`, the policy and
row-level-security changes, the function changes, materialized views, views with
indexes, index storage parameters, an access method other than b-tree, operator
classes, `NULLS FIRST/LAST` in an index, column comments, `serial` identity,
identity on anything but an `INTEGER` primary key, partitioning.

**Lock.** A row in `momo_migration_lock` (`id = 1`, `holder`, `acquired_at`),
created on first use. A second holder gets `ErrLocked` with
`held by pid=N host=H at=T`; `apply` polls it like the PostgreSQL lock until
`--lock-wait`. Unlock deletes the row only while it still carries this holder's
text. A process that dies leaves the row behind: after checking that nothing is
migrating, call `sqlite.ForceUnlock(ctx, conn)`, which returns the holder it
removed (there is no CLI flag). The lock and statement timeouts of the session
options do nothing on SQLite; busy handling is the driver's `busy_timeout`.

**Other differences.** DDL is transactional, so one migration is one
transaction. `AutoMigrate` skips any change to an existing table that needs a rebuild (an enum column, say) with the reason "requires a table rebuild; use a migration", because a rebuild writes the whole desired table and would also apply the changes AutoMigrate leaves alone (`TestSQLiteAutoMigrateSkipsRebuilds`). Index parts carry
no collation in the schema, so a collation on an index key is not compared.
Collation on a column is.

## 4. Failure and recovery

Check state with `momo migrate status` (exit 1 when anything is dirty,
mismatched or missing). Read `error`, shown after the colon.

### Transactional migration fails (`TestPostgresApplyRecovery`)

DDL and the history row roll back; nothing the file did persists. A
`rolled_back` row records the error. That is not dirty:
`status` shows `pending <v> <name>: <error>`, and the next `apply` retries
from statement 1. Fix the cause (or fix the file, section "editing", then
`momo migrate hash`) and run `apply` again. Data-exception errors (SQLSTATE
class 22) store only the code, not the message, because the message may quote
data.

### Interrupted (Ctrl-C, killed, lost connection)

- Transactional: the server aborts the transaction; no `running` row survives.
  Same as above. After a Ctrl-C, rollback and the failure row are still written
  (5 s bound).
- No-transaction: the `running` row was committed, so the version stays
  dirty (`running` or `failed`). The lock is released when the connection dies.

### No-transaction migration fails (partial state)

Statements before the failing one are committed. The row is `failed`, with
`statements_applied = n` and the error. Every later `apply` stops with
`ErrDirty` (`TestApplyRefusesDirtyAndReleasesLock`) until you resolve it.

1. `momo migrate status`, note the version and `statements_applied`.
2. Inspect the database. Statement `n+1` is the one that failed.
3. Make the database match one of two states by hand with `psql`:
   - finish the file yourself, then `momo migrate resolve --version V --applied`
     (the row becomes `applied`, error cleared, checksum of the file as it was
     when the run started is kept); or
   - undo the committed statements, then
     `momo migrate resolve --version V --rolled-back` (the row is deleted; the
     version is pending again and will run from statement 1). A file may be
     edited before the next apply: the version has no applied row, so edit,
     `momo migrate hash`, `apply`.
4. `resolve` takes the migration lock and errors when the version has no
   `running` or `failed` row.

### A down migration fails (`Engine.Rollback`)

A transactional down that fails rolls back with its history update: the schema
is unchanged and the row stays `applied`, so the database is not dirty
(`TestRollbackTransactionalFailureLeavesRowApplied`). Fix the down and run
`Rollback` again; if you edit the file, run `momo migrate hash` first.

A down with `-- momo:no-transaction` commits statement by statement. When one
fails the row becomes `failed` with `statements_applied = n` and an error that
starts with `down:`, and every later `apply` or `Rollback` stops with
`ErrDirty` (`TestRollbackNoTxFailureLeavesRowFailed`). Both resolve states are
valid; choose by what the database looks like after you repair it:

- `resolve applied` (`ResolveApplied`): the migration is still in effect. Use
  it when the failed down changed nothing that matters or you undid its
  partial work. The row becomes `applied`, the error is cleared, and the
  version can be rolled back again (`TestResolveAppliedAfterFailedDown`).
- `resolve rolled_back` (`ResolveRolledBack`): the migration is gone. Use it
  when you finished the down by hand. The row is deleted, the version is
  pending, and the next `apply` runs the up file again
  (`TestResolveRolledBackAfterFailedDown`).

`Rollback` verifies momo.sum first, down files included: an edited or added
`.down.sql` is refused with `ErrChecksumMismatch` naming the file even when the
matching up file is no longer in the directory
(`TestRollbackChecksumMismatch`). It takes the migration lock like `apply`
(`TestRollbackTakesTheLock`).

### Invalid index after a failed `CREATE INDEX CONCURRENTLY`

PostgreSQL leaves the index in place, marked invalid, when the build fails
(for example a uniqueness violation or a cancelled build). Momo does not use
`IF NOT EXISTS`, so re-running fails with "already exists" until you drop it.

1. `momo migrate drift` shows `changed: index <table>.<name>: invalid index (failed CONCURRENTLY build)`.
2. `DROP INDEX CONCURRENTLY IF EXISTS <schema>.<name>;` in `psql`.
3. Fix the data or definition.
4. `momo migrate resolve --version V --rolled-back` (if the row is `failed`),
   then `momo migrate apply`. If the failing file contained other statements,
   handle them per the previous subsection first.

`baseline` also counts an invalid index as a mismatch.

### Editing an already-applied migration

`apply` and `status` refuse (`checksum mismatch`, naming the file; status shows
`mismatch`). **`momo migrate hash` does not fix this.** It rewrites
`momo.sum`, but the history row still holds the old checksum, so `apply` still
refuses. Options:

- Revert the file (`git checkout -- <file>`), then write a new migration for the
  change. This is the supported path.
- If the edit is cosmetic (whitespace or a comment) and you accept it: run
  `momo migrate hash` (momo.sum), then `momo migrate rehash --version V` to see
  the recorded and the new checksum, then `momo migrate rehash --version V --accept`
  to store it. Without `--accept` nothing changes and the command exits 1 and says
  so. With it, only the row of version V is updated, and the row's `error` column
  records `checksum accepted by rehash at <time>: <old> -> <new>`, which `status`
  shows. The edit is accepted, not run: the database is not changed, so rehash
  only edits that do not alter what the migration did
  (`TestRehash`, `TestRehashOnPostgres`, `TestMigrateRehashAcceptsEditedMigration`).

Editing a migration that is not applied yet (status `pending`) is fine: run
`momo migrate hash` to accept it. `hash` records whatever is on disk, so review
the printed `changed:/added:/removed:` list first.

A history row whose file is gone shows `missing` and exit 1 on `status`.

### Idempotency

`apply` with nothing pending prints `no pending migrations`, exits 0, and
runs no migration. It takes the lock (an advisory lock, not a write) but writes
nothing: it does not create the history table or its meta row, so it works with a
read-mostly role. When something is pending, the history table is created first
(`TestApplyNothingPendingWritesNothing`,
`TestApplyNothingPendingCreatesNoHistoryTable`). Running it twice,
or two processes at once, is safe: the second waits for the lock, then finds
nothing to do (`TestConcurrentApply`, `TestConcurrentApplyWaits`).
`plan`, `status`, `drift` are read-only.

## 5. Production safety checklist

What Momo enforces, what it only hints at, what it does not see.
A complete worked upgrade (add column, index, rename) is `examples/upgrade-database`.

### Refused unless you opt in (`diff`, exit 1)

`--allow-destructive` is required for: `drop_table`, `drop_column`, `drop_enum`,
and a column type change (`alter_column` with a different type). The file then
carries `-- momo:destructive`. Review these. Type changes render as
`ALTER COLUMN ... TYPE ... USING col::type`: a full table rewrite under an
`ACCESS EXCLUSIVE` lock, which fails on rows that do not cast.

Not destructive, but reported as `risky:` hints by `diff` on PostgreSQL (no flag needed):
dropping an index, primary key, unique, check or foreign key; adding a unique
or check constraint (both can fail on existing data).

- `ADD CHECK` is written `NOT VALID`; its `VALIDATE CONSTRAINT` (a full scan
  that does not block writes) goes in the trailing no-transaction migration.
  If the validation fails, the trailing migration is `failed` and `apply` stops
  with `ErrDirty`. The constraint stays `NOT VALID`: it still checks new rows.
  Recovery: fix the offending rows, run
  `ALTER TABLE t VALIDATE CONSTRAINT c;` in `psql`, then
  `momo migrate resolve --version V --applied` (V is the `_no_tx` version).
  `resolve --version V --rolled-back` runs the whole file again from its first
  statement, so it is safe only when the file holds just the failed
  `VALIDATE`. If earlier statements of the file (a
  `CREATE UNIQUE INDEX CONCURRENTLY`, another `VALIDATE`) already committed,
  they would fail with "already exists": use `--applied` after finishing by
  hand, or undo those statements first (see "No-transaction migration
  fails").
- `ADD UNIQUE` on an existing table is `CREATE UNIQUE INDEX CONCURRENTLY`
  followed by `ADD CONSTRAINT ... UNIQUE USING INDEX`, both in the trailing
  no-transaction migration. On duplicate rows the build fails and leaves an
  `INVALID` index (`drift` reports it): drop it with
  `DROP INDEX CONCURRENTLY IF EXISTS`, fix the data, then `resolve --rolled-back`
  and re-apply (the unique index is the first statement of its file; if other
  statements of that file already committed, undo them first).
- On a partitioned table (including a sub-partitioned one) `ADD UNIQUE` is a
  plain, transactional `ADD CONSTRAINT ... UNIQUE`, and an index declared with
  `Concurrently()` is created and dropped without `CONCURRENTLY`, because
  PostgreSQL rejects `CONCURRENTLY` there. `ADD CHECK` keeps the `NOT VALID`
  form (`TestPartitionedTableConstraintsAndIndexes`).
- `diff` leaves out the explicit drop of an index, unique, foreign key or
  primary key that lists a column dropped in the same diff: `DROP COLUMN`
  removes it, and an explicit drop after it would fail. A check or an index
  expression or `WHERE` that merely mentions a dropped column's name anywhere
  in its text cannot be classified reliably, so its drop is written
  `DROP ... IF EXISTS`, which is correct whether or not the column took it.
- Limit: an inline foreign key in a new `CREATE TABLE` cannot reference a
  unique constraint that the same diff adds to another table, because that
  unique is created in the later no-transaction migration and the foreign key
  would fail. Workaround: run `diff` twice, first the unique on the existing
  table, then the new table with its foreign key.
- Not flagged at all: dropping a view, function, trigger or policy, and any
  change you write by hand.

The `-- momo:destructive` header is informational. `diff` writes it and
`--allow-destructive` is the only guard, and that guard exists in `diff` only:
`apply` does not read the header or scan statements, so a hand-written file
with a `DROP` applies without confirmation. Review every `.up.sql` in code
review.

### NOT NULL columns

An added `NOT NULL` column (or an existing column made `NOT NULL`) with no
default, identity or generation expression is refused (`ErrStagedRequired`)
for any table that already exists in the snapshot. `diff` never queries the
database, so it cannot tell whether the table has rows: an empty existing
table is refused too. A column that looks like a rename (same table and type
as a dropped column) is refused the same way; the message names
`--rename-column`. With `--stage`, then `--enforce-not-null`:

1. `diff --stage` adds the column as nullable and prints the hint
   `staged: T.C was added as nullable; backfill it, then run migrate diff with --enforce-not-null to emit ALTER TABLE T ALTER COLUMN C SET NOT NULL`.
   The new snapshot records the column as nullable, like the database will
   have it, so `validate` and `status` agree after you apply.
2. Apply, backfill in batches outside the migration.
3. Check the backfill: `SELECT count(*) FROM T WHERE C IS NULL` must return 0.
4. `diff <name> --enforce-not-null` emits
   `ALTER TABLE T ALTER COLUMN C SET NOT NULL` and records `NOT NULL` in the
   snapshot. A plain `diff` (without the flag) is still refused, because only
   you know the backfill is done. Apply it. The statement scans the table
   under a lock; do it when the table is quiet or add a validated `CHECK`
   first by hand.

Several columns can be staged in separate migrations before any backfill:
each stays recorded as nullable until enforced, and one `--enforce-not-null`
emits `SET NOT NULL` for all of them. The flag enforces every column that is
nullable in the snapshot and `NOT NULL` without a default in the model, not
only staged ones, so backfill all of them first. New `NOT NULL` columns stay
refused.

If NULLs remain, `apply` of the `SET NOT NULL` migration fails (exit 3). The
migration is transactional, so it rolls back: the version is `rolled_back`
(not dirty), `status` shows it as pending with the error, and nothing
changed. Finish the backfill and run `apply` again. Only a hand-edited
`-- momo:no-transaction` file can leave a dirty row; settle that with
`momo migrate resolve --version V --applied` or `--rolled-back` (section 4).

The same applies to an existing column made `NOT NULL`: `diff --stage` writes
nothing (the snapshot already has the column nullable; the hint is only
printed when the same run writes other changes), and `diff <name> --enforce-not-null` emits
the `SET NOT NULL` after the backfill. `--enforce-not-null` only affects
existing columns: a new `NOT NULL` column without a default still needs
`--stage`.

A `NOT NULL` column with a default is not staged. A constant default is cheap
on PostgreSQL 11 and later. A volatile default (`random()`,
`clock_timestamp()`, `gen_random_uuid()`, `nextval(...)` and a few more
well-known functions) rewrites the table under `ACCESS EXCLUSIVE`; `diff`
prints a `risk:` hint (PostgreSQL only) for an `ADD COLUMN` with one on an existing table. It
only knows the built-in names it lists; a function you wrote yourself is not
checked.

### Lint (`momo migrate lint`)

`momo migrate lint` reads the migration files and reports operations that lock
a table for long, rewrite it, or lose data. Each finding has a severity, the
rule, the version and 1-based statement number, and a safer alternative. It
needs no database: it checks every migration in the directory, or with `--db`
only the ones the database has not applied (`Engine.LintAll`, `Engine.Lint`,
`LintSQL`). It exits 1 when any finding is an `error`; warnings alone exit 0. A
table the migration creates itself is empty and never reported: a rule fires
only on a table of the parent snapshot (`TestMigrateLint`,
`TestMigrateLintQuietOnSafeSQL`, `TestMigrateLintExitCodes`).

| Rule                            | Severity | Fires on                                                                  | Alternative                                                             |
| ------------------------------- | -------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `not-null-without-default`      | error    | `ADD COLUMN ... NOT NULL` without `DEFAULT` (serial and generated exempt) | add nullable, backfill in a separate migration, then `SET NOT NULL`     |
| `not-null-without-default`      | warning  | `ALTER COLUMN ... SET NOT NULL` (the last step of the staged flow)        | backfill first; on a large table validate a `CHECK ... NOT VALID` first |
| `column-type-change`            | error    | `ALTER COLUMN ... TYPE`                                                   | add a new column, dual-write, backfill, switch reads, drop the old one  |
| `blocking-index`                | error    | `CREATE INDEX` without `CONCURRENTLY`                                     | `CREATE INDEX CONCURRENTLY` in a `-- momo:no-transaction` migration     |
| `foreign-key-without-not-valid` | error    | `ADD ... FOREIGN KEY` or `CHECK` without `NOT VALID`                      | add `NOT VALID`, then `VALIDATE CONSTRAINT` in a separate migration     |
| `enum-add-and-use`              | error    | `ALTER TYPE ... ADD VALUE 'x'` and a later statement that mentions `'x'`  | use the value in a later migration                                      |
| `destructive-without-directive` | error    | `DROP TABLE`, `DROP COLUMN`, `DROP SCHEMA`, `DROP TYPE`, `TRUNCATE`       | add `-- momo:destructive` after a review                                |
| `sqlite-rebuild`                | warning  | a statement with the SQLite `rebuild` hint (`LintSQL` callers)            | batch the data copy or split the table                                  |

The rules are text heuristics on the comment-free statement. The PostgreSQL
rules (the first six) run for the `postgres` dialect only; the destructive rule
runs for every dialect. A statement built inside a `DO` block or a function is
not seen, and a keyword inside a string literal can cause a false report.
`SET NOT NULL` is a warning, not an error, because the staged flow (below) ends
with it. The plan also sketches a `--db` row count rule for SQLite rebuilds;
`momo migrate` does not select SQLite, so it is not built.

### Other items

- **Backfills**: Momo has no data-migration step. Do them in a hand-written
  migration (section 6) or a separate job. A long backfill inside a
  transactional migration holds its locks until commit and can hit
  `lock_timeout`/`statement_timeout`.
- **Large-table indexes**: declare `Concurrently()` on the index in
  `MomoConfig`. `diff` then writes `CREATE INDEX CONCURRENTLY` in its own
  no-transaction migration, so the build does not block writes. Without
  `Concurrently()` the index is a plain `CREATE INDEX` that blocks writes while
  it builds. Set a role without `statement_timeout` for the run. A hand-written
  alternative: `examples/custom-sql-migration`.
- **Lock timeout**: the default 5 s lock wait fails fast instead of queuing
  behind a long transaction. A retry is safe for transactional migrations.
- **Deploy order**: migrate first, then roll out code, with every migration
  backward compatible with the running code (add before use; drop only after no
  code reads it; rename as add, copy, switch, drop).
- **Run once**: one `apply` job per deploy. Concurrent applies are safe but
  wait up to `--lock-wait`.
- **Backups**: take a backup or snapshot before any destructive, type-change
  or no-transaction migration. PostgreSQL DDL rolls back only inside a
  transaction; no-transaction files cannot be rolled back.
- **CI**: run `momo generate --check`, `momo migrate validate`, and the
  model-vs-migrations probe from section 1 on every change.
- **After**: `momo migrate status` (exit 0) and `momo migrate drift`.
- **Roles**: `CREATE EXTENSION` (pgvector, and any extension the models
  declare) needs a role allowed to create it. A missing package or privilege is
  reported, with exit 3, as
  `extension "x" is not installed (install its server package and run CREATE EXTENSION as a role that may)`.
  If a superuser creates the extension by hand, list it in
  `migrate.external_extensions` so no migration emits it (section 7).

## 6. Custom SQL migrations

Worked example: `examples/custom-sql-migration`.

`momo migrate new --custom <name>` (offline) writes the three files for an
empty hand-written migration: `<version>_<name>.up.sql` (comments only, no
`-- momo:generated`), `<version>_<name>.snapshot.json` (a copy of the latest
snapshot with the new version and that snapshot as its parent) and the extended
`momo.sum`. The name follows the `diff` rule (lowercase letters, digits and
underscores, starting with a letter). It needs an existing snapshot to copy:
run `diff` first (exit 2 otherwise), and it never overwrites a file (exit 1).
Write the SQL in the up file, then run `momo migrate hash` (the file changed
after `momo.sum` was written) and `momo migrate validate`.

You can also create the files yourself:

1. Choose a version greater than the latest and a name:
   `20260301120000_backfill_slug.up.sql`. Do not put `-- momo:generated` in it.
2. Optional directives at the top, before the first statement:
   `-- momo:no-transaction`, `-- momo:split`, `-- momo:destructive`
   (informational, never enforced), `-- momo:generated` (do not use it here)
   and `-- momo:sqlite-foreign-keys-off` (SQLite only; `apply` turns foreign keys off around the migration, section 3a). `-- momo:ddl` is not a
   file directive: it goes before one MySQL ALTER TABLE statement (section 9). An unknown `-- momo:` directive is an error.
3. Create `20260301120000_backfill_slug.snapshot.json` as a copy of the previous
   snapshot with `version` set to the new version and `parent` set to the
   previous version. The `schema` must stay equal to the parent's, or
   `validate` reports "custom migration ... must not change the schema".
4. `momo migrate hash`, `momo migrate validate`, then `apply`.

If the SQL changes the schema, change the models too and run `diff` afterward,
which compares against the latest snapshot as written; otherwise the next `diff`
will try to generate the same change again.

## 6a. Go migrations

A data step that SQL cannot express (a backfill that calls library code, the
templates an application ships in Go) is a `migrate.GoMigration`. It is
registered on the engine with `migrate.WithGoMigrations` and is ordered with the
SQL files by version, so it runs once, under the same lock, with a history row
(`kind = 'go'`) like any other migration.

<!-- docscheck:fragment -->

```go
g := migrate.GoMigration{
    Version:  "20260301120000", // 14 digits, unique among the SQL files too
    Name:     "backfill_templates",
    Checksum: "v1", // optional, see below
    Up: func(ctx context.Context, tx *momo.Tx) error {
        _, err := momo.Exec(ctx, tx, `UPDATE company SET templates_ready = true`)
        return err
    },
}
engine, err := migrate.NewEngine(drv, dir, migrate.WithDialect(pg), migrate.WithGoMigrations(g))
```

- **Transaction.** `Up` receives a `*momo.Tx`: the migration transaction that
  also holds the history rows. An error or a panic rolls everything back and
  records `rolled_back` (not dirty); the next apply runs it again. The
  function cannot commit or roll back that transaction.
- **No transaction.** Set `UpNoTx` instead of `Up` for work that cannot run in
  a transaction (`CREATE INDEX CONCURRENTLY`, a long backfill committed in
  batches). It receives a `*momo.DB` bound to the migration connection
  (`DB.OnConn`; it cannot begin a transaction). An error leaves the row
  `failed`, which is dirty: `apply` refuses with `ErrDirty` until you finish
  the work by hand and run `resolve` (section 4). Make the function safe to run
  again, because `resolve --rolled-back` runs it from the start.
- **Version.** A Go migration and a SQL file cannot share a version; `plan`,
  `apply` and `status` fail with an error naming the file, and `NewEngine`
  rejects two Go migrations on one version or a bad version or name.
- **Checksum.** Go code cannot be hashed. The recorded checksum is a hash of the
  version, the name and the optional `Checksum` string. When it differs from
  the applied row, `apply` refuses with `ErrChecksumMismatch` and `status`
  shows `mismatch`. Bump `Checksum` when you change what a migration does and
  want an already-migrated database flagged; leave it empty to bind only
  version and name.
- **Snapshot.** A Go migration has a snapshot file like a custom SQL migration
  (`<version>_<name>.snapshot.json`, a copy of the previous snapshot with the
  new version and `parent` set), and no up file. It must not change the schema.
  `migrate.ValidateOffline` checks that when you pass it the registered migrations after the directory, and that every
  registered Go migration has a snapshot; run it from a test of the application
  with the same migrations. `momo migrate validate` does not know the
  application's Go migrations, so it cannot check them. `diff` compares
  against the latest snapshot, a Go migration's included, and refuses while a
  registered Go migration has no snapshot file yet. Note for callers:
  `ValidateOffline` gained a variadic parameter, so a call without Go
  migrations compiles unchanged, but a function value of the old type no longer
  matches.
- **Forward only.** A Go migration has no down step. A rollback of the group
  that contains one refuses it: `Engine.Rollback` calls
  `migrate.RefuseGoRollback` with the history rows to roll back, before any down
  runs, and that returns `ErrGoMigrationNotReversible` for the first row of
  kind `go`; fix forward with a new migration.
- **Baseline.** `Baseline` through a version records a `go` row (checksum =
  the identity) for every registered Go migration up to it. An engine without
  that registration, the CLI included, refuses to baseline past a snapshot-only
  version with `ErrGoMigrationUnregistered`, because it cannot record the row.
- **Hooks and options.** Without `migrate.WithGoMigrationDB`, `Up` and `UpNoTx`
  get a bare `momo.New` of the engine's driver: none of the application's
  hooks, field hooks, clock or other options. Pass the application's `*momo.DB`
  (same driver) to `WithGoMigrationDB` to have its options apply.
- **The CLI cannot run them, and refuses to pass them.** `momo migrate apply`,
  `plan` and `status` read only the directory; a Go migration lives in the
  application's binary. The snapshot file marks its place: when the directory
  holds a snapshot with no up file, no registered Go migration and no history
  row, and a pending SQL migration has a later version, `apply` refuses with
  `ErrGoMigrationUnregistered` (exit 1) before it runs anything, telling you to
  run the application's `Engine.Apply`. Without that, the CLI would apply the
  later SQL and the application's engine would then fail with `ErrOutOfOrder`
  for the Go migration for good. Once the Go migration is applied, the CLI is
  unblocked; a database that has one in its history shows it as `missing` to
  the CLI. The check keys on the snapshot file, so a Go migration whose
  snapshot file is missing is invisible to the CLI: run `ValidateOffline` with
  your Go migrations in a test of the application, which reports that.
  The same refusal fires for an up file that was removed and left its snapshot,
  so when you squash old migrations remove their snapshots too. The
  application runs the engine itself, at start or in a small
  `cmd/migrate` of its own:

  <!-- docscheck:fragment -->

  ```go
  eng, err := migrate.NewEngine(drv, dir, migrate.WithDialect(pg), migrate.WithGoMigrations(g))
  if err != nil { /* ... */ }
  if _, err := eng.Apply(ctx, migrate.ApplyOptions{}); err != nil { /* ... */ }
  ```

  Use that binary for `apply`, and keep the CLI for `diff`, `hash`, `validate`
  and `drift`.

## 7. Adopting an existing database

Worked example: `examples/adopt-existing-schema`.

`momo generate --from-db` reads a live PostgreSQL database and writes the
models and the init snapshot, so nothing has to be written by hand first.

1. Run `momo generate --from-db DATABASE_URL`. The value is a database URL, `-`
   to read the URL from standard input, or the name of an environment variable
   that holds it; prefer the last two, because a URL on the command line is
   visible in the process list. It inspects the schemas named by
   `migrate.schemas` (default: the current schema), writes one
   `<table>_model.go` per table into the model package (`--out`, else
   `introspect.out`, else the first local entry of `packages`, else `./models`)
   and, when the migration directory has no snapshot, the init migration and
   snapshot. Do not apply the init migration.
2. Run `momo generate`, which writes the generated code for the new models.
3. `momo migrate baseline --version <init version>`. It checks the live
   database against that snapshot, including view, policy and trigger text, and
   exits 1 with `differing object kinds: ...` on a mismatch, then records every
   migration up to that version as `applied` with `statements_applied = 0` and
   `apply_id = baseline`, without running them. `--force` records anyway; use it
   only after reviewing the mismatch. Schema objects outside the models, such as
   extra extensions, count as a mismatch: add them to `migrate.exclude`. The
   run prints a hint for the extensions and skipped tables it found.
4. From then on use `diff` and `apply`.

The models carry exact table and column names (a `table` or `column` tag is
written wherever the naming preset would derive another name), Go types,
nullability (a pointer, or the `nullable` tag for slices), defaults, `size`,
`precision` and `scale`, enums, primary keys, identity (`identity` or
`identity:always`) and serial columns,
single-column indexes as tags, other indexes, unique constraints, checks and
comments in the `MomoConfig` method, every foreign key the generator can
derive as a `belongs_to` field with its `on_delete` and `on_update` actions
(with `fk_name` when the constraint name is not `<table>_<column>_fkey`;
PostgreSQL picks `_fkey1` on a partitioned table), and every composite
(multi-column) foreign key to a modeled table as a `c.ForeignKey(...)`
statement in `MomoConfig`. A composite primary key whose
column order differs from the field order is declared with
`c.PrimaryKey(&m.Name, &m.Scope, &m.At)` in `MomoConfig`; the DDL, inspection
and baseline keep that order. Changing the order of an existing key later is a
drop and add of the primary key under an `ACCESS EXCLUSIVE` lock, and the drop
is gated as destructive.
`numeric` columns are Go strings (the `decimal-as-string` note); an
`introspect.types` rule picks a decimal type instead. `tsvector` columns become
`types.TSVector` (`*types.TSVector` when nullable); an `introspect.types` rule
still overrides that.

`momo generate` leaves out type errors that come from files with momo's
generated header, since it rewrites them. After you rename or remove a field,
one `momo generate` run regenerates the stale file; an error in a hand-written
file still stops it.

A column type with no Go mapping is an error and nothing is written; add a rule
to the `introspect` section of `momo.yaml`. Constraints the models cannot
declare are left out of the models and the snapshot and printed as warnings, so
the two agree and the baseline reports them: foreign keys to a table with no
model, single-column foreign keys whose name is not table, column and `_fkey` or
that do not reference a single-column primary key, expression keys with an order or operator class, generated
columns, and PostgreSQL
schemas other than the current one.

### The introspect section

`momo.yaml` holds what the database cannot say, and it is applied again on every
run:

```yaml
introspect:
  package: models # default: the directory name
  out: ./models # default: the first local entry of packages
  skip: ["_prisma_*"] # table globs: no model, not in the snapshot
  only: [] # table globs: models only for these tables; skip applies within
  functions: "" # "all": every database function on the first model
  dbdefault: "" # "all": dbdefault on every NOT NULL column with a default
  types: # SQL type to Go type, for every column of that type
    inet: { go: string }
    numeric(12,2):
      { go: decimal.Decimal, import: github.com/shopspring/decimal }
  columns: # first to last; later rules win, tags add up
    - match: "*.updated_at" # glob over table.column
      tags: [updated_at]
    - match: "users.settings"
      go: "types.JSON[Settings]"
      name: Prefs # Go field name
  tables:
    users: { name: Account, tags: ["soft_delete:timestamp"] }
```

A rule's `tags` are momo tag options; one with the key of a generated option
replaces it. A Go type needs no `import` for `types.`, `vector.`, `time.`,
`json.` or `sql.`. Add skipped tables to `migrate.exclude` too, so the baseline
ignores the live tables.

`only` is the inverse of `skip`, for a project that moves onto momo one module
at a time: when it is set, a table that matches none of its globs gets no model
and no place in the init snapshot, and migrate (drift, baseline, diff) treats it
as excluded, so no `migrate.exclude` entry is needed for it. `skip` applies
within `only`. `only` limits tables only; views, functions and enums outside
your modules are hidden with `migrate.exclude`.

By default the models carry only the functions that a modeled table's triggers,
column defaults, generated columns, checks, index expressions and predicates or
policies call (and the functions those call), each on the model of the table
that uses it, and a table's triggers and policies are on its own model. A
function nothing modeled uses is not written. `functions: all` writes every
function on the first model, as releases before 0.7.0 did.

`dbdefault: all` tags every NOT NULL PostgreSQL column that has a default with
`dbdefault`, constant defaults such as `DEFAULT 1` included (by default only
computed defaults are tagged), so `Insert.Model` leaves an unset field to the
database default. A nullable column is never tagged. See "Database defaults" in
the [AI guide](ai-guide.md).

### Running it again

The schema keeps changing during a port. A re-run rewrites the model files that
nobody edited. Each file starts with a header that holds the hash of its body:
when the body still matches, the file is regenerated freely. A file with hand
edits, or one that `--from-db` did not write, is never replaced. A hand-edited
file stays quiet while the database has not changed its model; it conflicts
only when the regenerated model differs. The run writes
the regenerated version next to it as `<file>.new`, prints
`conflict: <file>`, and exits 1; merge the two by hand and delete the `.new`
file, or run again with `--overwrite` to take the regenerated one.
`--overwrite` only replaces a conflicting file: an edited file whose model the
database did not change stays as it is. A file whose
table is gone is printed as `orphan` and never deleted. `--check` writes
nothing, prints `stale: <file>` for each difference and exits 1. The init
snapshot is written once: when the migration directory already has a snapshot,
use `diff` for later schema changes. Put code of your own in other files and
rules in the `introspect` section, and a re-run stays quiet.

`baseline` needs `CREATE` on the database for the canonicalization step when
the snapshot has views, functions, triggers or policies, **or any table with
text PostgreSQL rewrites**: a column default or generation expression, a check
constraint, an index predicate or an index expression. A snapshot of plain
tables, columns, keys and plain indexes needs no such privilege
(`TestBaselineAsAppRole`). `--force` does not waive it: the error is
`ErrCanonicalizePrivilege`, naming the privilege, and nothing is recorded
(`TestBaselineAsAppRoleNeedsCreateForTableText`). Run the baseline once as a
role that has `CREATE` on the database (for example the owner role), or grant it
for that run. It takes the lock and refuses on dirty or checksum problems like
`apply`.

### Roles and extensions (verified)

Checked on CI with a role that is not a superuser and has no `CREATE` on the
database:

- `CREATE EXTENSION IF NOT EXISTS vector` **succeeds** when the extension
  already exists (PostgreSQL only emits a notice; it checks existence before
  privileges). So the statement that a generated migration emits is harmless for
  that role once a superuser has installed pgvector
  (`TestAppRoleExtensionIfNotExists`). When the extension is not installed the
  statement needs a privileged role, as before.
- `baseline` and `apply` run `CREATE TABLE IF NOT EXISTS` for the history table.
  PostgreSQL checks `CREATE` on the schema before it looks for the table, so a
  role with only `USAGE` on the schema is refused with the error
  `permission denied for schema` even when it owns an existing
  `momo_migrations` (`TestBaselineAsAppRoleNeedsCreateOnSchema`). The migrator role needs `CREATE`
  on its schema: `GRANT CREATE ON SCHEMA app TO app_role`.
- With `CREATE` on the schema but not on the database, `baseline` works for a
  snapshot without table text (`TestBaselineAsAppRole`) and fails with
  `ErrCanonicalizePrivilege` otherwise (section 7). `drift` fails with it when
  the snapshot declares a view, a trigger `WHEN` or a policy expression, and
  runs without it for table text only, listing the tables in
  `CanonicalizeSkipped` (`TestDriftBodiesNeedCreateOnDatabase`,
  `TestDriftTablesOnlyRunsAsApplicationRole`).

### Extensions managed outside momo

Set `migrate.external_extensions` in `momo.yaml` for an extension that a
superuser installs by hand:

```yaml
migrate:
  external_extensions: [vector]
```

Names are exact. For each listed extension momo

- never emits `CREATE EXTENSION` from `diff` (or `AutoMigrate`), even when a
  model has a `vector` column, and keeps it out of the snapshot it writes;
- does not report it from `drift`, and does not count it as a mismatch in
  `baseline`, even though the live database has it.

The migrations then no longer create the extension, so a new environment must
get it before the first `apply`. Use it only when that is the intent. It differs
from `migrate.exclude`, which hides unmanaged objects of every kind from drift
and baseline but does not stop `diff` from emitting `CREATE EXTENSION` for a
model that needs it. If a snapshot already declares the extension, the setting
hides it on both sides, so no drop or create is generated either.

A database that uses `serial` or `bigserial` ids is adopted with the `serial`
tag, as in `pk,serial` on an `int64` field. The tag renders `smallserial`,
`serial` or `bigserial` by the Go integer width. Inspection reads a column
whose default is `nextval` of a sequence owned by the column back as the same
serial column, so the snapshot matches and `diff` stays empty. `serial` is
PostgreSQL only; other dialects refuse it. Turning an existing column into or
out of serial is refused by `diff`, with an error that asks for a
hand-written migration.

Upgrade note: inspection used to report a serial column as `identity`. If you
adopted a serial database with `pk,identity` on the model, or kept a snapshot
taken from one, `diff` now stops with `column "id" is a serial column in the
database but the model declares identity`. Change the tag to `pk,serial` and
regenerate the snapshot; or write a migration that converts the column to
identity. Momo does not treat the two as equal, because a new environment
would then be built with identity while production keeps its serial.

`AutoMigrate` is a Go API for development and tests. It applies additive
changes only, writes no history and no files, and returns the rest as
`Skipped`. Do not mix it with versioned migrations on one schema.

## 7a. Cutover from Prisma `db push` to momo

Playbook for a database whose schema is changed by `prisma db push` and
hand-written idempotent SQL files (`DO $$ ... IF NOT EXISTS` guards, `GRANT`
lines, a hand-created extension), moving to momo owning the DDL. Rehearse every
step on a copy of production.

1. **Models first.** Write the momo models so they match the live database
   (section 7). Columns Prisma generates in the client, such as cuid ids, are
   not in the database; model them as plain columns.
2. **Declare what you do not own.** Put the extension a superuser installs in
   `migrate.external_extensions`. Put tables, views and functions that stay
   outside the models (an analytics schema, an audit table, Prisma's
   `_prisma_migrations`) in `migrate.exclude`. Roles, grants and sequences
   outside a column are not part of the schema model; they stay in hand-written
   SQL.
3. **Write the initial migration.** `momo migrate diff init` against an empty
   directory. Do not apply it. Read the generated SQL: it is what a new
   environment would run, and it must build the schema you have.
4. **Rehearse the baseline** on a copy, with
   `momo migrate baseline --version <init version>`, as a role with `CREATE` on
   the database (section 7). Exit 1
   lists the differing object kinds. Fix the models or `exclude` until it is
   clean. Do not use `--force` to skip a difference you have not read.
5. **Dual-writer period: momo watches, it does not write.** While Prisma still
   pushes, the database moves under momo. Do not baseline production yet and do
   not apply migrations. Run `momo migrate drift` against a baselined copy, or
   the rehearsal in step 4 against production, on a schedule. A table Prisma
   added shows as `unmanaged:`, a new column in a managed table as
   `changed: ... not in snapshot`, and an altered column as `changed:`. Each is
   a task: put it in the models, or in `exclude`. Drift cannot see changed view,
   trigger or policy text (section 1).
6. **Freeze `db push`.** Stop `prisma db push` in every environment (remove it
   from the deploy). Update the models to the final live state and, since
   nothing was applied, delete the unapplied `init` files and run `diff init`
   again, so the initial snapshot is the schema as it is at the freeze.
7. **Baseline each environment.** In each environment run
   `momo migrate baseline --version <init version>` once, then
   `momo migrate drift` (expect `no drift`). The role that runs `apply` needs
   `CREATE` on the schema (section 7). From then on `apply` runs only newer
   migrations. A database created from scratch runs the init migration; it needs
   the external extension installed first.
8. **Hand off.** Schema changes go through `diff`; backfills and other data
   changes through `momo migrate new --custom`, which replaces the hand-written
   SQL files. Leave guards such as `IF NOT EXISTS` out of new files: the
   history says what ran.

Undo: baseline only writes history rows, so drop the `momo_migrations` table to
return to the state before step 7; nothing else changed.

## 8. Security

- `momo` redacts connection strings from everything it prints (stdout, stderr,
  error text, and bad flag values that a pasted URL lands in): URL userinfo
  becomes `***@`, a URL in text that has a query keeps the part before `?` and
  shows `?***`, a `password=`/`passwd=`/`pwd=` value becomes `***`, and the
  exact URL and password given are replaced by `***`.
  History `error` text is the server message only, never `Detail`. Messages of
  SQLSTATE class 22 (data exception) are withheld because they can contain
  data values. Connection URLs and `password=` values in the text are replaced
  by `***` before it is stored (`TestHistoryErrorIsRedacted`).
- A warning on stderr (not a failure) when a command that needs a database is
  given a URL with `sslmode=disable` and any non-local host:
  `TLS is not enforced (sslmode=disable) for remote host H: credentials and data can cross the network unencrypted; use sslmode=verify-full`.
  It names the hosts only. It also fires when the URL or key=value string has
  no `sslmode` (libpq then uses `prefer`, which falls back to plaintext), for
  `allow` and `prefer`, for key=value connection strings, and when `sslmode`
  comes from `PGSSLMODE`; a host missing from the string is read from
  `PGHOST`. `localhost`, `127.0.0.1`, `::1`, unix socket paths and no host at
  all do not warn, and neither do `require`, `verify-ca` and `verify-full`.
  `require` encrypts but does not check the server's identity, so use
  `sslmode=verify-full` against a real server.
- Do not pass the URL with `--url` on shared hosts (momo warns); use
  `migrate.url_env`, `MOMO_DATABASE_URL` or `--url -` (stdin).
- Review `*.up.sql` in code review like any code: `apply` runs it as the
  connected role, and `momo.sum` only detects change, not intent.
- Tamper detection is against accidental edits, not an attacker.
  `momo migrate hash` rewrites `momo.sum` to match whatever is on disk, and
  `momo migrate rehash --accept` stores the checksum of whatever file is on
  disk in the history row. Both trust the files completely: anyone who can edit the
  migration files and run those commands can make an edited migration pass
  every check. Protect the migration directory with code review and write
  access control, and the database with the migrator role's grants; `momo.sum`
  does not.
- `drift` and `baseline` execute model DDL on the target database. To compare
  declared text with what the database reports, they create a scratch schema
  and run the declared definitions (defaults, checks, index predicates, view
  queries, function bodies, policy and trigger expressions) in a transaction
  that is rolled back. That needs `CREATE` on the database, runs SQL taken
  from your snapshots and models, and takes locks while it runs. Run them
  against a scratch database restored from a backup, or a clone, rather than
  production.

## 9. MySQL and MariaDB

The `migrate/mysql` package is the migration dialect for MySQL 8.4, MySQL 9.7
and MariaDB 11.8. It reads `information_schema`, renders DDL and locks with
`GET_LOCK`. `momo migrate` does not select it yet; build the engine with
`migrate.WithDialect(mmysql.New())` and the `mysqldriver` driver.

**Every migration is non-transactional.** DDL implies a commit on these
servers, so a failure cannot be rolled back. The engine runs each statement on
its own, records `statements_applied` after each one, and leaves a failed row
that is dirty until you repair the database and run `resolve`. This holds with
or without `-- momo:no-transaction`, for Go migrations, and for `rollback`: a
down that fails half-way leaves its earlier statements applied and the row
failed. Write each
migration so that a half-applied run is easy to finish by hand.

**Locking.** `GET_LOCK` names are server-wide, so the lock name carries the
database (`momo:<database>.momo_migrations`, cut to the 64 characters MySQL
allows, with a hash suffix when the key is longer). The lock belongs to the
pinned connection and is released with `RELEASE_LOCK`, or when the connection
ends. A busy lock returns `migrate.ErrLocked` with the connection id of the
holder.

**Session timeouts.** The lock timeout becomes `lock_wait_timeout`, the time a
statement waits for a metadata lock, in whole seconds. A statement timeout
becomes `max_statement_time` on MariaDB; on MySQL it is refused with
`momo.ErrUnsupported`, because `max_execution_time` bounds SELECT only.

**Online DDL.** A line `-- momo:ddl ALGORITHM=INPLACE, LOCK=NONE` directly
before an `ALTER TABLE` statement appends those options to it. MySQL rejects
`LOCK=NONE` together with `ALGORITHM=INSTANT`; use `ALGORITHM=INSTANT` alone. The server
rejects the statement when it cannot honour them, so a change that would copy
the table fails instead of running slowly. Without the directive momo adds no
`ALGORITHM` or `LOCK` clause. Only `ALGORITHM=` and `LOCK=` options are
accepted.

**What inspection reports.** One database is inspected, the connection's
default, and the history table is left out.

- A UNIQUE constraint and a unique index are the same object on these servers.
  A unique key made of plain ascending columns is reported as a unique
  constraint; declare such keys as constraints.
- The index MySQL creates for a foreign key, named after the constraint, is
  not reported, and the diff refuses a declared index that has the name of a
  foreign key of its table, because the two would collide and could not be
  told apart. An index of a database you adopt that already has such a name
  and the key's columns is treated as the server's own.
- `NO ACTION` is reported as an empty action. MariaDB reports its default as
  `RESTRICT`, so on MariaDB `RESTRICT` and an unwritten clause are one.
- MariaDB stores `json` as `longtext` with a `json_valid` check named after the
  column; the pair is reported as type `json`.
- A column is reported with a collation only when it differs from its table's
  default; declare `Collate` on the column to pin one.
- Defaults that the servers store alike are one default: `NOW`, `LOCALTIME`
  and `CURRENT_TIMESTAMP`; `TRUE` and `FALSE` are `1` and `0`. `RESTRICT` and
  `NO ACTION` are the same foreign key action.
- Stored CHECK text is compared without the identifier quotes, character set
  introducers and the parentheses MySQL adds around each comparison. Other
  rewrites by the server (for example `!=` stored as `<>`) show as a
  difference of text; write the expression the way the server stores it.
  Parentheses around a comparison are removed only between and, or and xor,
  so `(a between 1 and 2) and c > 0` keeps them and differs from the same
  text without them; a backslash escape inside a string is kept as written.
- A foreign key into another database is reported as `database.table`.
- Integer display widths (`int(11)` on MariaDB) are no difference of type.
  Identifier quotes, character set introducers and outer parentheses in stored
  expressions are no difference of text.
- An index part with a prefix length is the column name followed by the length
  in parentheses, such as `name(10)`. Index visibility, character sets and
  `ON UPDATE CURRENT_TIMESTAMP` are not part of the schema model, and a
  `MODIFY COLUMN` that a type change renders restates the column without them:
  an `ALTER` of such a column is a migration to write by hand.

**Rendering.** Tables are `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4`. An identity
column is `AUTO_INCREMENT` (`by_default`; `always` and `serial` are refused). A
default that is not a literal or `CURRENT_TIMESTAMP` is wrapped in parentheses,
as MySQL requires. Partial indexes, storage parameters, operator classes,
enums, views, functions, triggers and policies have no MySQL rendering yet and
are refused. The `hash` index method is refused: InnoDB builds it as BTREE. Dropping a
foreign key also drops the index MySQL built for it, when one exists, unless
another foreign key of the table starts with the same column: that key may rely
on the index, and dropping it would fail after the key was gone. The index then
stays and shows as an index named like the dropped key; declare it, or drop it
once nothing needs it. An
AUTO_INCREMENT column must be a key in the statement that adds it, but the
engine adds a primary key in a separate statement after the column: add such a
column and its key in a migration you write yourself. Declare a generated
column as nullable: MariaDB does not take
`NOT NULL` on one. MySQL refuses a CHECK, or a stored generated column, on a
column that a foreign key with a referential action uses.

## Upgrading: generated file header

Generated Go files start with `// Code generated by momo (format 1). DO NOT EDIT.`.
The header carries the generated-file format number, which decides
compatibility, and no momo release version, so a later momo upgrade does not
rewrite generated files whose code is unchanged. Earlier releases wrote the
same line with a release version between `momo` and `(format 1)`; momo still
recognises that form, so orphan detection keeps working.

After upgrading, run `momo generate` once. Until then `momo generate --check`
reports the header change in every generated file.
