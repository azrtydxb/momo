    Momo guide for AI coding agents¶

    Target: github.com/azrtydxb/momo v0.7.0. Read this file instead of the Momo source. Every identifier below was checked against v0.7.0. Where the guide says DON'T, the call either fails, silently does the wrong thing, or is a known bug.

    Imports used throughout:

    import (
    "github.com/azrtydxb/momo"                    // core: DB, Tx, Select, Insert, Update, Delete, errors
    "github.com/azrtydxb/momo/driver/pgxdriver"   // PostgreSQL driver (pgx v5)
    "github.com/azrtydxb/momo/vector"             // vector.Vector, HalfVector, SparseVector, Bits
    "github.com/azrtydxb/momo/types"              // types.UUID, Date, Numeric, JSON[T], TimeOfDay, Hstore, TSVector, TSQuery
    "yourmodule/models"                           // your structs
    "yourmodule/models/task"                      // GENERATED: one package per model (lowercase model name)
)

    Deeper docs: README, relations, migrations, vectors, capabilities, supported versions, type mapping, architecture, examples.

    1. Scope¶

    • v0.7.0 supports PostgreSQL 16 and 17 with pgvector 0.8.x, through pgx v5; the other databases are in the status block below.

    Database status:

    A database is usable when a driver package for it exists under driver/:

    • PostgreSQL: usable through driver/pgxdriver (vector builders: yes). Migrations: migrate/postgres, run by momo migrate.
    • SQLite: usable through driver/sqlitedriver (needs cgo, not on Windows, vector builders: yes) and driver/sqlitepure (vector builders: no). Migrations: migrate/sqlite, library only (momo migrate does not select it).
    • MySQL and MariaDB: usable through driver/mysqldriver (vector storage and builders depend on the server version). Migrations: migrate/mysql, library only (momo migrate does not select it).
    • PostgreSQL is the reference database. Check the dialect columns of docs/capabilities.md before relying on a feature on another database. Keep dialects: at [postgres] for generated migrations. momo migrate exits 2 for a dialect it does not link; library migrations go through migrate.NewEngine.
    • Go 1.26.10 or newer (the go.mod floor, which carries the standard-library security fixes). Pre-v1: no compatibility promise; pin the exact version.
    • diff writes forward migrations only. momo migrate rollback [--group] runs a hand-written .down.sql, momo migrate lint reports risky operations, and momo migrate rebase --onto <dir> regenerates a branch's migrations on a target's.
    • momo generate --from-db DATABASE_URL turns a live PostgreSQL database into models and an init snapshot (see migrations). Other databases: write models by hand.
    • Reciprocal-rank-fusion hybrid search is momo.HybridSearch (PostgreSQL only, see vectors.md). Full-text search (types.TSVector, fts.Match, fts.RankCD, fts.Headline, the query builders) exists on PostgreSQL; to weigh the signals yourself, combine a vector distance with a text rank in one score as shown in fulltext.md.

    Details: capabilities.md. Example: quickstart.

    2. Install and tooling¶

    go get github.com/azrtydxb/momo@v0.7.0                # adds the library to go.mod and writes go.sum
go install github.com/azrtydxb/momo/cmd/momo@v0.7.0   # the CLI: generate, migrate, import, viz, help

    Run go get first in a fresh module: it produces go.sum, which go run and the generated code's compilation need. go install puts momo in $(go env GOPATH)/bin; make sure that is on PATH.

    Layout of a project (the models package holds structs; momo generate writes into it):

    go.mod
momo.yaml
models/models.go          # yours
models/momo_gen.go        # generated (MomoMeta for each model). Commit it.
models/task/momo_gen.go   # generated: columns and relations of Task. Commit it.
migrations/               # momo migrate diff writes here. Commit it.

    Minimal momo.yaml (at the module root; the CLI finds it by walking up to go.mod):

    version: 1
packages:
  - ./models
dialects: [postgres]
migrate:
  dir:
    postgres: migrations
  url_env:
    postgres: DATABASE_URL

    naming: is optional: momo (default: snake_case columns, plural snake_case tables), gorm, bun, ent, prisma. Pick one and never change it: a change renames columns. The momo preset keeps an initialism together, and a plural s after it belongs to it: RoleIDs is role_ids, URLs is urls, HTTPServer is http_server.

    naming: prisma matches a database that Prisma created: the table is the model name as written and quoted (KbChunk), the column is camelCase (createdAt, accountId; an ID word at the end becomes Id, and a trailing IDs becomes Ids, so UserIDs is userIds), and the constraint and index names are <Table>_pkey, <Table>_<col>_fkey, <Table>_<col>_key (unique) and <Table>_<col>_idx. Those names come out of the table and column names, so no tag is needed for single-column keys and indexes.

    Limits of the preset:

    • A composite @@index or @@unique is named by Prisma from all its columns (<Table>_<a>_<b>_idx). Name such an index explicitly in MomoConfig or with an index:/unique: tag name.
    • The implicit many-to-many table is named _AToB (model names in alphabetical order), but its A and B columns and its foreign key names are not reproduced. Declare that table with an explicit join model instead.
    • A column name that does not follow the camelCase rule needs a column: tag.

    Prisma maps DateTime to timestamp(3), so add a types: section:

    naming: prisma
types:
  time.Time: timestamp(3)

    types: overrides the default PostgreSQL column type of a Go type. Only time.Time is supported, and the value must be timestamp, timestamptz, time or timetz with an optional precision 0-6 and an optional with/without time zone (anything else is refused, as it is written into DDL). A type: tag on a field still wins. It applies when the first entry of dialects is PostgreSQL (or dialects is empty); with SQLite first it is ignored. Without it time.Time is timestamp with time zone.

    Generate:

    //go:generate momo generate

    momo generate            # writes *_gen.go
momo generate --check    # CI: exit 1 and "stale: <path>" lines when stale; writes nothing

    Rules:

    • DO run momo generate after every change to a model struct or tag, before compiling code that uses the generated packages.
    • DO commit generated files. DON'T edit *_gen.go and DON'T name your own files *_gen.go (the generator refuses to overwrite non-generated files).
    • DO put *_gen.go text eol=lf in .gitattributes if anyone uses Windows, to keep checkouts byte-identical (--check already treats a CRLF copy as current).
    • DON'T use go run of the CLI inside app code; the library (momo) never imports the generator.

    Details: README "Configure and generate". Example: quickstart.

    3. Connecting¶

    func openDB(ctx context.Context, url string) (*momo.DB, func(), error) {
    pool, err := pgxdriver.NewPool(ctx, url) // (ctx, string) (*pgxpool.Pool, error)
    if err != nil {
        return nil, nil, err
    }
    return momo.New(pgxdriver.New(pool)), pool.Close, nil // New(pool, opts ...Option) momo.Driver
}
    • The caller owns and closes the pool. momo.DB has no Close.
    • *momo.DB is safe for concurrent use; create one at startup and share it.
    • DSN: postgres://user:password@host:5432/dbname?sslmode=verify-full. Use sslmode=disable for local development only. Momo adds no TLS options; pgx reads sslmode, sslrootcert, ... from the URL.
    • Read the URL from the environment, never hard-code credentials.
    • Pool sizing: Momo documents no recommendation and sets nothing. pgxpool options (for example pool_max_conns=N in the URL) apply. Each open Tx, vecsearch.With block, Replace and CreateGraph holds one connection for its whole duration.

    Other constructors:

    sqlDB, drv := pgxdriver.FromConnConfig(cfg, opts...) // cfg *pgx.ConnConfig; returns (*sql.DB, momo.Driver)
drv = pgxdriver.FromSQLDB(sqlDB)                     // sqlDB must be backed by pgx stdlib; for an existing *sql.Tx see SQLTx, AdoptTx and UnwrapSQLTx in section Transactions

    database/sql paths have no Batch or COPY path (relation loading falls back to sequential statements; correct, just slower).

    PgBouncer (transaction pooling):

    • pgxdriver.New defaults to pgx.QueryExecModeExec (unnamed statements, server-side binding). That is PgBouncer-safe; set nothing.
    • That mode sends no parameter types, so the driver converts what pgx cannot encode. []uuid.UUID (github.com/google/uuid), []types.UUID and any slice of a [16]byte type that implements fmt.Stringer bind to id = ANY(?::uuid[]) (with or without the cast; a nil slice is NULL). A raw []byte is bytea text and a jsonb column rejects it: pass the JSON as json.RawMessage or string, or use types.JSON[T]. The pgxdriver tests TestUUIDSliceBindsToAnyArray and TestJSONBBinding pin this.
    • pgxdriver.WithExecMode(m) accepts pgx.QueryExecModeCacheStatement, pgx.QueryExecModeCacheDescribe, pgx.QueryExecModeDescribeExec (import github.com/jackc/pgx/v5; not tested through PgBouncer). The simple protocol is rejected with ErrUnsupported on every query. DON'T select it.
    • With FromConnConfig set cfg.DefaultQueryExecMode = pgx.QueryExecModeExec first; pgx defaults to CacheStatement, which is NOT PgBouncer-safe. Its opts have no effect.
    • DON'T run momo migrate through a transaction pooler (section 5).
    • Set search_path per role or per transaction, not at connection startup.

    Details: capabilities.md "Getting connected", supported-versions.md "PgBouncer".

    4. Modeling¶

    A model is a struct that embeds momo.Model BY VALUE. The tag on that embedded field names the table. The tag grammar is momo:"opt,opt:value,..."; a value cannot contain a comma. An unknown, duplicate or malformed option is a generator diagnostic and nothing is written for that package.

    type Account struct {
    momo.Model `momo:"table:accounts"`
    ID         int64      `momo:"pk,identity"`
    Email      string     `momo:"size:200,unique"`
    Plan       string     `momo:"size:20,default:'free',index"`
    Note       *string    `momo:"size:500"`                         // pointer = nullable
    Balance    int64      `momo:"default:0"`
    Version    int64      `momo:"version,default:0"`                // optimistic lock
    CreatedAt  time.Time  `momo:"column:created_at,created_at"`     // set by Momo on insert
    UpdatedAt  time.Time  `momo:"column:updated_at,updated_at"`     // set by Momo on update
    DeletedAt  *time.Time `momo:"column:deleted_at,soft_delete:timestamp"`
    Embedding  vector.Vector `momo:"dim:1536"`                      // pgvector column

    Posts []Post `momo:"has_many,fk:AccountID"`
}

    Nullability and column rules:

    • A non-pointer Go field is NOT NULL. A pointer (*string), a sql.Null* type, or the nullable tag makes the column nullable. notnull is redundant for non-pointers and a diagnostic on pointers.
    • A nullable field generates momo.NullColumn[T] (has SetNull()); a non-nullable one generates momo.Column[T] (SetNull() does not compile). For a *T value that may be nil, col.SetPtr(p) writes NULL when p is nil and *p otherwise, and col.EqPtr(p) renders IS NULL when p is nil and = $n otherwise. Do not branch on nil by hand.
    • A primary key must not be nullable.
    • Scanning NULL into a non-pointer field is an error. Use pointers for nullable columns. The one exception is a dbdefault pointer, which is NOT NULL (see Database defaults).
    • Go type to column type: see TYPE_MAPPING.md (int is bigint, string is text, string with size:N is varchar(N), time.Time is timestamptz, types.UUID is uuid, types.JSON[T] is jsonb). uint64, maps and unknown types have no mapping: add type:<sql> or a codec.
    • JSON columns: jsonop.Text, jsonop.Path, jsonop.Contains and jsonop.HasKey (package github.com/azrtydxb/momo/jsonop) are typed operators over a types.JSON[T] column; the extractions are string expressions usable in Where, OrderBy and Columns. An extraction is NULL for a missing key and for JSON null alike, a SQL NULL column is tested with IsNull on the column, and the JSON literal null is matched by comparing the column with a types.JSON whose value is nil. jsonop.HasKey is true for a key whose value is JSON null. A numeric key in jsonop.Text or jsonop.HasKey is an object key; only jsonop.Path elements made of digits can be array indexes. SQLite renders json_extract and json_type (jsonop.Contains is ErrUnsupported there); MySQL renders its JSON functions.
    • JSON edits and scalars: jsonop.Root(col) reads a scalar stored at the root of the value (col #>> '{}'; cast it with sqlfn.Cast for a number). jsonop.DeleteKey(expr, key) is expr - 'key' (SQLite json_remove, MySQL JSON_REMOVE), so a snapshot keeps every future column and still drops the secret. jsonop.Concat(a, b) is the shallow a || b and jsonop.Set(target, path, value) is jsonb_set with a path built in SQL (momo.ArrayOf(...)). Both are PostgreSQL only and ErrUnsupported elsewhere, because json_patch and JSON_MERGE_PATCH merge recursively and drop nulls. jsonop.DeleteKey, jsonop.Concat and jsonop.Set need jsonb on PostgreSQL: the -, || and jsonb_set forms do not exist for json. Their results are JSON expressions that jsonop.Text, jsonop.Path, jsonop.Root and jsonop.HasKey accept again, typed as the first operand without a check, so a mismatch shows only when the row is scanned. A SQL NULL value in jsonop.Set makes the whole result NULL: wrap an optional value in COALESCE. jsonb_build_object and to_jsonb are variadic "any": cast their bound arguments (sqlfn.Cast), as PostgreSQL cannot type a bare parameter there.
    • Column names default to the naming preset (CreatedAt becomes created_at). Fields are exported only; a tag on an unexported field is a diagnostic. Skip a field with momo:"-".

    Tag reference (all lower case):

    Tag Meaning
    table:<name> (on momo.Model) table name; always set it. Also schema:<name>.
    pk primary key; several pk fields make a composite key, declared in field order unless Config.PrimaryKey lists the fields in another order (a tag belongs_to target needs a single-column key)
    identity, identity:always database-generated identity (GENERATED BY DEFAULT AS IDENTITY; identity:always is GENERATED ALWAYS AS IDENTITY, so a client-supplied value is refused by the database; not on MySQL)
    serial PostgreSQL smallserial/serial/bigserial id by Go int width (sequence owned by the column, DEFAULT nextval); omitted from inserts and read back with RETURNING like identity; excludes identity and default; refused on other dialects
    column:<name> column name
    size:<n> varchar(n); strings only
    precision:<p>, scale:<s> numeric precision (float, decimal, or a string without size that carries a numeric); scale needs precision
    dim:<n> vector dimension; optional on vector and halfvec (none: dimensionless column), required on sparsevec and bit, invalid elsewhere
    default:<sql> column default, raw SQL (default:now(), default:'free', default:0)
    unique / unique:<name> unique index (single column)
    index / index:<name> index; modifiers sort:asc\|desc, nulls:first\|last, method:<m> need index or unique
    idgen:<name> client-generated string id (cuid, uuid, ulid or a name registered with WithIDGenerator); filled on insert when the field is empty
    dbdefault leave the column to the database default while the field holds its zero value (nil for a pointer field, which then writes false and 0 when set): a Model/Models insert omits it and reads the stored value back (see Database defaults)
    generated:<expr> stored generated column (GENERATED ALWAYS AS (<expr>) STORED); needs read_only, so Insert and Update never write it while Select and Where can use it; an insert does not read it back (select the row again, or use ReturningAll where the dialect has RETURNING). An expression with a comma goes through Config.Generated. --from-db writes both
    virtual with generated:<expr> (or Config.GeneratedVirtual): the column is VIRTUAL (computed on read) instead of STORED. MySQL and SQLite only: a PostgreSQL target is refused (VIRTUAL needs PostgreSQL 18, momo supports 16 and 17). An error without generated. --from-db writes it for a VIRTUAL column
    version optimistic-lock column (integer type)
    created_at[:unix\|unixmilli\|unixnano], updated_at automatic timestamps; field type time.Time, *time.Time, int64 or *int64
    soft_delete:timestamp\|unix\|bool soft-delete marker; Go type *time.Time, *int64 or bool
    read_only, create_only, immutable write permissions: never written; written on insert only; never updated
    sensitive excluded from the generated ColumnByName allowlist (use for secrets)
    type:<sql>, collate:<c>, check:<expr>, comment:<t>, enum:<name> raw column type, collation, check, comment, enum type
    embedded, prefix:<p> flatten a named struct-typed field into this table (anonymous embedded structs flatten by themselves); prefix prepends to its column names
    nullable, notnull explicit nullability (rarely needed)

    MomoConfig for what tags cannot express: composite or partial indexes, vector indexes, checks, enums, views, triggers, policies. The generator reads this method statically and never runs it; arguments are &receiver.Field pointers and string literals only.

    func (a *Account) MomoConfig(c *momo.Config) {
    c.Unique("accounts_email_plan_key", &a.Email, &a.Plan)
    c.Index("accounts_plan_live_idx", &a.Plan).Where("deleted_at IS NULL")
    c.Index("accounts_embedding_hnsw", &a.Embedding).
        Method("hnsw").
        Opclass(&a.Embedding, "vector_cosine_ops").
        With("m", "16").With("ef_construction", "64")
    c.Check("accounts_balance_nonneg", "balance >= 0")
}

    An index name declared in MomoConfig must not collide with an auto-named <table>_<col>_idx produced by an index tag (the Plan field above already yields accounts_plan_idx); the generator refuses the duplicate.

    Config methods: Config.Index, Config.IndexExpr, Config.Unique, Config.ForeignKey, Config.Check, Config.Enum, Config.Default, Config.Generated, Config.Comment, Config.Collate, Config.IDGen, Config.FKName, Config.PrimaryKey, Config.View, Config.Function, Config.Trigger, Config.Policy, Config.RLS, Config.Partition, Config.PartitionOf. Index chain: IndexOpts.Unique() (on Config.Index or Config.IndexExpr), Where(pred), Method(m), IndexOpts.With(k, v), Opclass(field, op), Desc(field), Nulls(field, "first"|"last"), Concurrently() (diff writes the index as CREATE INDEX CONCURRENTLY in its own no-transaction migration).

    A unique expression index is Config.IndexExpr with IndexOpts.Unique(): c.IndexExpr("principal_email_key", "lower(email)").Unique(). Each string is one key: an expression, or the exact name of a column of the table, which is a plain column key, so c.IndexExpr("template_name_key", "company_id", "lower(name)").Unique() indexes (company_id, lower(name)). Add Where("deleted_at IS NULL") for a partial one. It is an index, not a constraint, so it cannot be a foreign key target. generate --from-db writes unique, mixed and partial expression indexes back this way; an expression key with DESC, NULLS or an operator class has no declaration.

    A composite (multi-column) foreign key is declared in MomoConfig, not with a tag: c.ForeignKey("note_document_fk", []any{&n.CompanyID, &n.DocumentID}, "document", []string{"company_id", "id"}).OnDelete("CASCADE"). The first list holds &receiver.Field pointers, the table name and the referenced columns are string literals, and OnDelete/OnUpdate take CASCADE, RESTRICT, SET NULL, SET DEFAULT or NO ACTION. The referenced table must be the table of a model, and the referenced columns, in any order, must be its primary key, a unique constraint (c.Unique) or a non-partial unique index over plain columns; otherwise the generator reports a diagnostic. The key is a plain constraint: diff adds, replaces and drops it like a single-column key, and generate --from-db writes it back. There is no belongs_to form for a composite key; the relation still needs a single-column key.

    Many-to-many needs join: with the same table on both models you declare it on (the reverse side is optional, but if declared it must carry join: too):

    type Document struct {
    momo.Model `momo:"table:documents"`
    ID         int64 `momo:"pk,identity"`
    Title      string
    Tags       []Tag `momo:"many2many,join:taggings"` // join table taggings(document_id, tag_id)
}

type Tag struct {
    momo.Model `momo:"table:tags"`
    ID         int64 `momo:"pk,identity"`
    Name       string
    Documents  []Document `momo:"many2many,join:taggings"` // optional reverse side, same join table
}

    Relation tags (a relation is an exported field of struct, slice or pointer type; it is not a column):

    Tag Field type FK lives on Notes
    belongs_to,fk:<Field> *Target this struct fk names the FK field on THIS struct; make it a pointer if the relation is optional
    has_one,fk:<Field> *Target the target fk names the field on the TARGET
    has_many,fk:<Field> []Target the target fk names the field on the TARGET
    many2many,join:<table> []Target join table set join: (same table) on every side you declare; the reverse side is optional; two key columns <model>_<pkcol>

    Extra relation options: polytype:<column> + polyvalue:<value> (both, on has_one/has_many only: polymorphic), on_delete: / on_update: (cascade, restrict, set_null, set_default, no_action; they affect only the FK emitted for belongs_to), no_constraint (emit no FK), fk_name:<name> (constraint name when not <table>_<col>_fkey; or Config.FKName(&m.FKField, name)). has_one and has_many create no FK constraint themselves; the belongs_to on the other side does. Many-to-many join tables get a composite primary key plus two FKs with ON DELETE CASCADE.

    Generator diagnostics (nothing is written for the package until fixed): more than one relation kind on a field; field type does not match the kind; target is not a Momo model; fk missing or naming a missing field; many2many without join:, or a declared reverse side without join:; polytype without polyvalue (or the reverse), or on a kind other than has_one/has_many; polytype column not a field of the target; many-to-many to the model's own type; momo.Model embedded by pointer; a generic model; size on a non-string; dim on a non-vector; sparsevec or bit field without dim; scale without precision; notnull on a pointer; nullable primary key; unknown tag option; Go type with no SQL mapping.

    What the generator emits per model Task (package task):

    • task.Table (a momo.TableRef), one column variable per field (task.ID, task.Title), task.As("t") for aliased columns, task.ColumnByName(name) and task.ColumnNames() (an allowlist for user-supplied sort/filter names).
    • One momo.Relation[Parent, Child] per relation field (document.Comments, document.Author).
    • Vector fields become momo.VectorColumn[vector.Vector] (nullable: NullVectorColumn).
    • read_only / create_only / immutable fields become permission-typed columns that have no Column.Set (or insert-only Column.Set).
    • Package name = lowercase model name. It can collide with your local variable names (task := ... shadows the package). Name variables differently or alias the import.

    Client-generated ids¶

    Databases that keep ids as text and generate them in the client (Prisma @default(cuid())) have no column default to lean on. Declare the generator on the field, with the tag or in MomoConfig:

    package main

import "github.com/azrtydxb/momo"

func main() {}

type Contact struct {
    momo.Model `momo:"table:contacts"`
    ID         string `momo:"pk,idgen:cuid"`
    Name       string
}

type Note struct {
    momo.Model `momo:"table:notes"`
    ID         string `momo:"pk"`
}

func (n *Note) MomoConfig(c *momo.Config) { c.IDGen(&n.ID, "ulid") }
    • Built-in generators: cuid (25 characters in the layout Prisma writes, so old and new ids look alike), uuid (random, version 4, 36 characters) and ulid (26 characters, sortable by creation time). Register your own, or replace a built-in, with momo.New(drv, momo.WithIDGenerator("short", fn)) and tag idgen:short. Names are lowercase; the MomoConfig form takes a string literal.
    • The generator fires when an insert writes the field and it holds the Go zero value: Model, Models, Upsert and every chunk of a bulk insert. An id you assigned is kept. The generated id is stored in your struct (the model you passed, or the slice element), so read m.ID after Exec or Rows.
    • The field must be a string kind (named string types and *string work). Any other type, a name given twice (tag and MomoConfig) or identity/serial on the same field is refused by the generator. A name that is neither built in nor registered fails the insert with ErrValidation.
    • A column named in Omit always takes a fresh generated id, which is bound and written back like any other. InsertQuery.Values and InsertQuery.ValuesRows that leave the id out get one too. SQL() shows a generated id in the arguments but does not store it in the model.
    • On an OnConflict upsert whose target is not the primary key, the row in the database may keep its own id. Exec then asks the database for the stored id and writes that into the model (a DoUpdate that hit an existing row gives that row's id). A model whose row DoNothing skipped keeps the id it had, usually empty. This needs RETURNING; without it (MySQL) the id is not written back for such statements. Rows never writes back there: read the id from the returned rows.
    • When the id is written back up front (every statement except the conflict case above), it stays in your struct also when the insert fails. Retrying the same struct reuses the id, and so do all rows of a failed chunked insert. Clear the field to get a new one. In the conflict case the model is updated only after a successful statement.
    • In the conflict case, rows are matched to models on the conflict-target columns (or on the generated id for DoNothing without a target), so those columns must read back exactly as you wrote them; citext, char(n) and numeric columns may not. A returned row that matches no model fails with ErrValidation and the write is rolled back; only a pinned OnConn handle, which cannot open a transaction, keeps it. If two models share a target value, the first one is matched. A non-primary-key generated column (such as a public_id) counts as a conflict case too, because the kept row has its own; the default DO UPDATE set of Upsert leaves such a column out, so a conflict never replaces the stored value, even one you assigned; to overwrite it, pass an explicit DoUpdate that sets it. A single-statement insert that reads ids back runs in its own transaction (or savepoint), so a mismatch rolls the write back, and the models are updated only after the whole insert has committed. Inside your own Tx that means after the savepoint is released, not after your outer commit: if you roll the outer transaction back, the models still hold the ids of rows that no longer exist.
    • The generator is a client-side convenience, not a secret. A cuid is built from the time, a counter and a process fingerprint, so it is guessable: do not use it for tokens or anything that must be unpredictable. Use uuid (random, version 4) or your own generator for that.
    • A generator that returns an empty id, panics, or is registered with a nil function fails the insert with ErrValidation. The ulid generator does the same in the unlikely case that it runs out of ids within one millisecond.
    • The tag adds no database default: the column stays text primary key.

    Database defaults¶

    InsertQuery.Model writes every writable column, so a column with DEFAULT gen_random_uuid() or DEFAULT now() is overwritten by the Go zero value. Tag the field dbdefault to leave it to the database instead:

    package main

import (
    "time"

    "github.com/azrtydxb/momo"
)

func main() {}

type Event struct {
    momo.Model `momo:"table:events"`
    ID         string    `momo:"pk,type:uuid,default:gen_random_uuid(),dbdefault"`
    Title      string
    OccurredAt time.Time `momo:"default:now(),dbdefault"`
}
    • When the field holds its zero value (the Go zero value, a nil pointer, or a value whose IsZero method reports true, such as time.Time{}), Model and Models leave the column out of the INSERT, so the database default applies, and Exec reads the stored value back with RETURNING into the struct you passed (the slice element for Models) once the statement has committed. A non-zero value is written as given. A pointer to a zero value counts as set.
    • Models with a mix of zero and set rows writes DEFAULT for the zero rows (PostgreSQL). SQLite cannot put DEFAULT in a multi-row VALUES list, and Unnest and Copy have no per-row default, so they fail with ErrUnsupported for such a mix: insert the rows separately or give every row a value. A column that is zero in every row simply leaves the column list. Copy has no RETURNING to read the value back, so it refuses a zero dbdefault column with ErrUnsupported: set a value, or use Models.
    • MySQL has no RETURNING, so a zero dbdefault column fails with ErrUnsupported there instead of leaving the struct stale: set the value, or leave it out with Omit and read it yourself. MariaDB and SQLite read it back with RETURNING.
    • Your own Returning list turns the automatic read-back off; Rows returns the columns you named. A single Model that a conflict action skips (DoNothing) returns no row: Exec reports 0 rows affected and leaves the model as it was. A bulk Models insert that returns fewer rows than models (a conflict action, a trigger or a rule dropped some) is matched by key when it can be: the key is the conflict target, else the primary key, it must be written from the model (not omitted, identity or read-only) and must not be a dbdefault column that is zero in some row. The key is then added to the RETURNING list, the returned rows are written back by key and the other models stay untouched; the insert fails only when the conflict action is DoNothing and a skipped model still has a dbdefault column unread. When the rows cannot be matched by key the insert fails with ErrUnsupported ("returned N rows for M models"), rolls back and writes nothing back: give the columns a value, or use Returning and Rows. Inside a caller's Tx the rollback is to a savepoint, not the caller's transaction, which stays open. A pinned OnConn handle cannot roll back: it returns the same error, says the returned rows were stored, and writes nothing back. The conflict-target column of an insert that also uses an id generator cannot be a dbdefault column that is zero in some row (ErrValidation). The default DO UPDATE set of Upsert leaves a dbdefault column out when a row leaves it to the database, so a conflict keeps the stored value.
    • The zero value means "use the default". On a plain bool or numeric field that means false and 0 can never be written explicitly through Model: a dbdefault field with DEFAULT true always stores true when it is false in Go, and momo generate warns about such a field. The same holds for an empty string and a zero time. To write false or 0, make the field a pointer on a NOT NULL column (Active *bool with `momo:"default:true,dbdefault"`): a nil pointer takes the database default and is set to the stored value after the insert, a non-nil pointer is always written, false and 0 included. The column stays NOT NULL. A sql.Null* type or the nullable tag is refused by the generator, because nil would stop meaning NULL; write NULL with InsertQuery.Values and SetNull. Omit still wins: an omitted column is not written, and a Go-side default hook still fills it.
    • Update(...).Model(&m) treats a nil dbdefault pointer as "not set": it leaves the column out of SET, so the column keeps its stored value (writing NULL would fail on the NOT NULL column). A pointer to false or 0 is written. If that leaves nothing to set, the update fails with the usual ErrValidation ("no columns to update"). Upsert is unaffected: its default DO UPDATE set takes EXCLUDED values and already leaves out a dbdefault column that any row leaves to the database.
    • The pointer type that --from-db generates and the momo generate warning cover only plain bool and number fields (bool, int..int64, uint..uint64, float32, float64). A named type, a type override from introspect.types or introspect.columns, a decimal or a string keeps the field as it is and gets neither the pointer nor the warning.
    • dbdefault cannot be combined with identity, serial, idgen, read_only, version, soft_delete, created_at or updated_at; the generator reports it. It adds no database default (use default:), and momo generate --from-db writes it for NOT NULL PostgreSQL columns whose default is computed (a function call, CURRENT_TIMESTAMP, or a nextval sequence on a column that is not identity or serial); with introspect.dbdefault: all it writes it for every NOT NULL column that has a default, a constant one such as DEFAULT 1 included; a bool or number column whose constant default is true or non-zero becomes a pointer field, so an explicit false or 0 is written. A hand-written model can put dbdefault on any NOT NULL column that has a database default. It never writes it for other dialects: plain MySQL cannot read the value back.

    Model hooks¶

    Give a model a method named BeforeInsert, BeforeUpdate, BeforeDelete or AfterLoad with the exact signature func(context.Context) error and momo generate wires it into Meta.Hooks; nothing else to register. A method with a hook name and another signature fails the generator with a positioned diagnostic, and a hook-named method on a projection is a diagnostic too (projections run no hooks). The semantics (which builders run which hook, the copy BeforeInsert receives, the error kind) are in the HookSet documentation. DON'T edit Meta.Hooks in generated code.

    View models¶

    A model that maps a database view embeds momo.View next to momo.Model:

    type ActiveUser struct {
    momo.Model `momo:"table:active_users"`
    momo.View
    ID int64 `momo:"pk"`
}

    The generator sets Meta.View. Reads work as for any model; Insert, Upsert, Update, SoftDelete, BulkUpdate, Delete and Merge return ErrValidation naming the model, at run time (there is no compile-time check). Declare the view itself with c.View(schema.View{...}) in MomoConfig. The schema the generator builds holds that view and no table for the view model, so a migration never issues CREATE TABLE for it, and no foreign key refers to it. Materialized: true declares a materialized view; refresh it with momo.RefreshMaterializedView(ctx, db, "name", false) (a name with a schema prefix, two parts joined by a dot, is split and quoted; the last argument adds CONCURRENTLY, which needs a unique index in the view's Indexes). It is PostgreSQL only and returns ErrUnsupported elsewhere.

    Generated servers¶

    The momo binary has built-in graphql, grpc and openapi plugins, enabled in the plugins section of momo.yaml. They generate servers over your models with no authentication or authorization: wrap them. The openapi and grpc plugins take ops, read_only and on_error; the OpenAPI document has a <Model> output schema and a <Model>Input request schema. See capabilities for the options, error mapping and limits.

    Custom generator binary¶

    The momo binary runs no custom plugins. To run your own gen.Plugin, write a main that calls cli.Main(plugins...) from github.com/azrtydxb/momo/cli and build it; it behaves as momo does and the plugins are enabled by name in the plugins section of momo.yaml.

    Projections¶

    A projection reads a column subset or aggregate into a non-table struct. Embed momo.Projection by value; momo generate emits its MomoMeta into momo_gen.go (every exported field, in declaration order; column name from the naming rule or a momo:"column:..." tag). NEVER hand-write MomoMeta for a projection. The Columns(...) list of the query must equal the struct field order.

    type Card struct {
    momo.Projection
    ID    int64
    Title string
    Score int64
}

    Use it like this:

    cards := momo.Select[models.Card](q).From(article.Table).
    Columns(article.ID, article.Title, article.Score).
    OrderBy(article.ID.Asc()).
    All(ctx)

    When From is a plain generated table (article.Table) with a soft-delete column (timestamp, unix or bool), the live-row filter is added automatically, exactly as for a model; WithDeleted() and OnlyDeleted() work too. Do NOT add Where(<table>.DeletedAt.IsNull()) yourself. A Join does not change this: the From table is filtered and joined tables are not. To alias use article.Table.As("a"), which keeps the filter. The filter is NOT added when From is a subquery or CTE, or a hand-built momo.TableRef{Name:..., Alias:...} (it has no soft-delete column): filter those yourself.

    If a package still has a hand-written projection MomoMeta from before the generator emitted it, delete it (method and Meta variable); the generated one redeclares it.

    A projection cannot be inserted, updated or deleted (it embeds Projection, not Model). Computed columns (a distance, momo.CountAll()) are valid entries in Columns. The select list is positional and not aliased: the name you give a computed column in Columns of the meta (for example distance) is only a label.

    Tuple rows: for an aggregate, join or few-column read use momo.Row1 to momo.Row10 instead of declaring a projection (no struct, no generated meta). Columns is scanned positionally into the fields C1 to Cn:

    counts, err := momo.Select[momo.Row2[string, int64]](q).From(article.Table).
    Columns(article.Title, momo.CountAll()).GroupBy(article.Title).All(ctx)
// counts[i].C1 is the title, counts[i].C2 the count

// SUM is NULL over no rows: a pointer type parameter reads it as nil
total, err := momo.Select[momo.Row1[*int64]](q).From(article.Table).
    Columns(momo.Sum(article.Score)).One(ctx)
// total.C1 is nil when no article matches

    A Columns count different from the arity is ErrValidation (no statement is sent). Tuple rows are read-only projections: the same soft-delete rule as above applies to the From table, and After needs a unique key in OrderBy. NEVER hand-write a projection Meta for a tuple shape.

    Examples: projection-pagination, vector-search (Hit).

    Details: TYPE_MAPPING.md, relations.md section 1. Example: relations.

    5. Migrations workflow¶

    Flow: edit models, momo generate, momo migrate diff <name>, REVIEW the SQL, commit, momo migrate apply.

    momo generate
momo migrate diff add_plan              # offline; writes 3 files into migrations/
momo migrate diff init                  # first run on an empty dir: the initial schema
momo migrate plan                       # list pending (needs DB)
export DATABASE_URL='postgres://user:pass@host:5432/app?sslmode=verify-full'
momo migrate apply                      # [--to N] [--lock-wait 30s]
momo migrate status                     # applied | pending | dirty | mismatch | missing
momo migrate drift                      # live DB vs latest applied snapshot
    • diff writes <version>_<name>.up.sql, <version>_<name>.snapshot.json and rewrites momo.sum. Commit all three. diff never overwrites; the name must match ^[a-z][a-z0-9_]*$; the version is a 14-digit UTC timestamp.
    • diff compares models with the latest snapshot, never with the database. Prints no changes and writes nothing when equal.
    • Never edit an applied migration file, even cosmetically: apply refuses on the changed checksum. For a cosmetic edit you accept: momo migrate hash, then momo migrate rehash --version V --accept (without --accept it only shows the two checksums); see migrations.md section 4. Prefer a new migration.
    • Renames are never guessed: a rename looks like drop plus add and is refused. Say it explicitly: --rename-column table.old=new, --rename-table old=new.
    • Destructive changes (drop_table, drop_column, drop_enum, a column type change) are refused without --allow-destructive. Type changes rewrite the table under ACCESS EXCLUSIVE and fail on rows that do not cast.
    • A NOT NULL column without a default on a table that exists in the snapshot is refused (migrate.ErrStagedRequired). Give it a default:, or stage it: diff --stage, apply, backfill, check SELECT count(*) FROM t WHERE c IS NULL is 0, then diff --enforce-not-null. The flag enforces every nullable column the model has as NOT NULL, not only staged ones; with NULLs left, apply fails (exit 3) and rolls back cleanly (not dirty): backfill and apply again.
    • URL: --url (warns: visible in the process list; --url - reads stdin), else migrate.url_env.postgres, else MOMO_DATABASE_URL. Exit codes: 0 ok, 1 findings, 2 usage/config, 3 database/lock/execution error. An invalid migration name (diff Bad-Name) exits 3, not 2.
    • Hand-written SQL migration: momo migrate new --custom <name> writes the up file (no -- momo:generated line), a snapshot copied from the latest one and the extended momo.sum; write the SQL, then momo migrate hash and momo migrate validate. The snapshot schema must equal its parent's. Directives (first lines): -- momo:no-transaction, -- momo:split, -- momo:destructive (informational). Unknown -- momo: directive is an error.
    • Existing database: write models, momo migrate diff init (do not apply), then momo migrate baseline --version <init version>; the live schema must match the snapshot (extra objects: add globs to migrate.exclude). Example: adopt-existing-schema.
    • The first migration with a vector column runs CREATE EXTENSION IF NOT EXISTS "vector". pgvector must be installed on the server (image pgvector/pgvector), and the migration role must be allowed to create extensions, otherwise apply exits 3 naming the extension. An extension a superuser installs by hand goes in migrate.external_extensions in momo.yaml: no migration emits it and drift ignores it.

    CI (every change):

    go install github.com/azrtydxb/momo/cmd/momo@v0.7.0
momo generate --check                                   # generated code is current
momo migrate validate                                   # files vs momo.sum, version chain, forks, snapshots
momo migrate diff ci_probe | grep -qx 'no changes'      # models have a migration

    The last line is derived from the code, not covered by a test: when models changed, diff writes files (exit 0) and grep fails the job; discard the files (git checkout -- migrations && git clean -fd migrations). There is no diff --check. validate already verifies momo.sum; do not run momo migrate hash in CI.

    Production checklist:

    1. momo migrate validate and momo migrate plan before apply; read the SQL.
    2. One apply job per deploy, over a DIRECT connection (not PgBouncer in transaction mode: the lock is a session advisory lock).
    3. Migrate first, then roll out code; every migration must be backward compatible with the running code (add, backfill, switch, drop later; a rename is add, copy, switch, drop).
    4. Back up before any destructive, type-change or no-transaction migration.
    5. Use a migration role without statement_timeout; migrate.lock_timeout defaults to 5 s and fails fast on a blocked DDL (safe to retry).
    6. After: momo migrate status (exit 0) and momo migrate drift.
    7. Failed transactional migration: nothing persists; fix and re-run. Failed no-transaction migration leaves partial state and a dirty row: finish or undo by hand in psql, then momo migrate resolve --version V --applied or --rolled-back. Full procedure: migrations.md section 4.

    Known issues, as rules (each is a filed bug):

    • For large tables declare Concurrently() on the index in MomoConfig: diff writes CREATE INDEX CONCURRENTLY in its own -- momo:no-transaction migration (a trailing <name>_no_tx file when the diff also has other DDL). Without it the index is a plain CREATE INDEX that blocks writes. A failed concurrent build leaves an INVALID index: drift reports it; drop it with DROP INDEX CONCURRENTLY IF EXISTS, then resolve --rolled-back and re-apply.
    • -- momo:no-transaction applies to the WHOLE file: every statement loses atomicity and a mid-file failure leaves earlier statements committed (dirty). diff never mixes modes: it splits concurrent indexes, ADD UNIQUE and VALIDATE CONSTRAINT into a trailing no-transaction migration and keeps the transactional DDL in the first file. Keep hand-written no-transaction files to one statement.
    • -- momo:destructive is informational: diff writes it, apply does not read it, so a hand-written DROP applies without confirmation. The only guard is diff --allow-destructive. Review every .up.sql like code.
    • diff prints risky: hints for dropping an index, primary key, unique, check or foreign key and for adding UNIQUE/CHECK; these need no flag. ADD CHECK is emitted NOT VALID with a later VALIDATE CONSTRAINT, and ADD UNIQUE as CREATE UNIQUE INDEX CONCURRENTLY plus USING INDEX. Both can still fail on existing violating data. Hand-written changes are not flagged.
    • NEVER edit an applied migration. apply and status refuse (migrate.ErrChecksumMismatch) and momo migrate hash alone does NOT fix it (the history row keeps the old checksum). Preferred: git checkout -- <file> and write a new migration. A cosmetic edit you accept: hash, then momo migrate rehash --version V --accept. Editing a still-pending migration is fine; then run hash. hash accepts every edit, so read its changed:/added:/removed: list first.
    • apply refuses a forked snapshot chain (same error as validate) and a pending version older than the latest applied one (migrate.ErrOutOfOrder); both exit 1, as does a broken chain (migrate.ErrChainInvalid). Fix it with momo migrate rebase --onto <target branch's migration directory>, or by hand: delete the late migration's .up.sql and .snapshot.json, run momo migrate diff <name> to regenerate it with a new version, then momo migrate hash (a pending file needs no rehash); see migrations.md section 2. Still run validate in CI.
    • momo migrate rollback [--group] runs the hand-written .down.sql of the last applied migration (or group); diff never writes one. Without a down file it exits 1 and runs nothing; prefer a new forward migration. resolve --rolled-back runs no SQL.
    • There is no --force-unlock (an unknown flag, exit 2). The migration lock is a session advisory lock, freed when its holder disconnects. A stuck lock: find the session in pg_stat_activity and pg_terminate_backend it.
    • migrate.lock_timeout: 0s and statement_timeout: 0s disable the timeouts (SET ... = 0); leave the key out for the defaults (5 s, untouched).
    • apply with nothing pending writes nothing, not even the history table.
    • --url is visible in the process list (momo warns): use migrate.url_env, MOMO_DATABASE_URL or --url -. URLs in history error text are redacted.
    • momo_migrations lives in the first schema of search_path; migrate.schemas[0] must equal current_schema() or the engine errors.
    • Dropped extensions and schemas are not dropped in the database.
    • AutoMigrate (Go API) is additive only, writes no history; DON'T mix it with versioned migrations on one schema.

    Details: migrations.md. Examples: upgrade-database, custom-sql-migration, adopt-existing-schema.

    6. Queries cheat sheet¶

    All builders take a momo.Querier (*momo.DB or *momo.Tx), so write helpers that accept momo.Querier and call them inside or outside a transaction. Builders are immutable values: every method returns a copy. Values are always bound ($1...); identifiers come from generated columns. Errors from building (bad column, wrong shape) surface at SQL() or at the terminal call.

    Select:

    tasks, err := momo.Select[models.Task](q).
    Where(task.Done.Eq(false), task.Priority.Ge(2)). // several predicates are ANDed
    OrderBy(task.Priority.Desc(), task.ID.Asc()).
    Limit(20).Offset(0).
    All(ctx) // []T; an empty result is a nil slice and nil error, never ErrNotFound

one, err := momo.Select[models.Task](q).Where(task.ID.Eq(id)).One(ctx)   // ErrNotFound / ErrTooManyRows
first, err := momo.Select[models.Task](q).OrderBy(task.ID.Asc()).First(ctx) // ErrNotFound when empty
n, err := momo.Select[models.Task](q).Where(task.Done.Eq(true)).Count(ctx)  // int64; ignores order and After
ok, err := momo.Select[models.Task](q).Where(task.Title.Eq("x")).Exists(ctx)

    Predicates on columns: Eq Ne Lt Le Gt Ge In NotIn Between IsNull IsNotNull IsDistinctFrom IsNotDistinctFrom InQuery NotInQuery and *Expr variants; combinators momo.And, momo.Or, momo.Not, momo.Like, momo.ILike, momo.ContainsLiteral, momo.Exists(subquery), momo.NotExists. momo.EscapeLike(s) escapes user text for Like. Find NULLs with IsNull(); Eq(nil) is not expressible.

    Array columns (a PostgreSQL type). A []string field is generated as text[]; []int16, []int32, []int64, []bool, []float32, []float64 and []types.UUID map to smallint[], integer[], bigint[], boolean[], real[], double precision[] and uuid[]. The predicates are generic functions over a typed column, in the package github.com/azrtydxb/momo/arrayop: arrayop.Contains(col, vals...) (@>), arrayop.ContainedBy (<@), arrayop.Overlaps (&&) and arrayop.AnyOf(scalarCol, vals...) (= ANY($n)). Each binds the values as one array parameter, so the bind count does not grow with the list. arrayop.Overlaps and arrayop.AnyOf with no values are false. On other dialects they fail the build with ErrUnsupported; use In there. Array expressions: momo.ArrayOf[T] renders ARRAY[e1, e2] from column, call or momo.Value elements (an empty list is ErrValidation), and momo.ArraySubquery[T] renders ARRAY(subquery) for a one-column SelectQuery or momo.Union. Both are Expression[[]T], so they scan into a []T field and feed arrayop predicates; PostgreSQL only.

    Searching with user input safely. Like and ILike always render ESCAPE '!' on every dialect, matching EscapeLike. Wildcards (%, _) in the pattern still work; only a ! makes the next character literal, so a hand-written literal ! is written !!. Never concatenate raw user text into a pattern. For a substring search use momo.ContainsLiteral with the column and the user text; it is case-sensitive on PostgreSQL, while SQLite and MySQL follow their own LIKE and collation rules. For a case-insensitive search on PostgreSQL, pass ILike a pattern built as a percent sign, the user text run through momo.EscapeLike, and another percent sign. A user typing % then matches only a literal percent sign, never every row.

    A backslash is not an escape character. Without an ESCAPE clause PostgreSQL and MySQL treat \ as the LIKE escape; in momo a pattern such as \% means a literal backslash followed by a wildcard. Replace hand-escaped patterns with momo.EscapeLike, or write !% for a literal percent sign.

    In, NotIn and tuple IN bind one parameter per value. A list over the dialect bind limit (PostgreSQL 65535, MySQL 65535, SQLite 32766, or a lower WithMaxParams) fails at build time with ErrValidation, not at the driver. The check counts the binds rendered before the list; binds rendered after it are left to the driver. Cap or chunk request-supplied lists yourself. An empty In renders a constant false and an empty NotIn a constant true.

    Two independent caps apply to a typed In or NotIn list. WithMaxInList(n) limits the number of values per list and fails the build with ErrLimitExceeded; it is for request-supplied lists. The bind limit above is the database ceiling for the whole statement and fails with ErrValidation. Both are checked at build time, the list cap first, so the stricter one wins. SelectQuery.MaxRows(n) is the matching cap on results: All and Pluck return ErrLimitExceeded instead of more than n rows, never a truncated slice.

    Other builder methods: Distinct, Join, LeftJoin, CrossJoin, GroupBy, Having, ForUpdate (with the options "NOWAIT" or "SKIP LOCKED"), ForShare, ForNoKeyUpdate and ForKeyShare (PostgreSQL only: FOR NO KEY UPDATE does not block foreign-key inserts on the locked row, FOR KEY SHARE is the weakest lock; same options; MySQL and SQLite return ErrUnsupported), LockOf (names the tables a lock covers, for example ForUpdate("SKIP LOCKED").LockOf("d") on a joined job claim; the names must be table or alias names, not CTEs), SelectQuery.With, WithRecursive, Union (a member with its own ORDER BY, LIMIT, OFFSET or lock is parenthesised, a derived table on SQLite), SelectUnion[T] (runs a union at the top level with an outer OrderBy, Limit and Offset; All, Rows), FromSubquery, Each (a context and a callback per row) and Iter (a context; it returns iter.Seq2[T, error]). Count and Exists wrap the whole statement, so they keep a lock clause and lock the rows they count. Aggregates: momo.CountAll, CountOf, CountDistinct, Sum, Avg, Min, Max.

    Advisory locks (PostgreSQL, inside a transaction), in the package github.com/azrtydxb/momo/advisory: advisory.XactLock(ctx, tx, key) waits for a transaction-scoped lock on an int64 key, advisory.TryXactLock returns whether it was granted, and the string variants (advisory.XactLockString, advisory.TryXactLockString) hash a text key with hashtext; pass advisory.Hash64(seed) to hash with the 64-bit hashtextextended(key, seed) instead (seed 0 matches pg_advisory_xact_lock(hashtextextended(key, 0)) in existing SQL). The lock ends at commit or rollback. They take a *Tx, so a *DB does not compile: open a transaction first. Other dialects fail with ErrUnsupported. Never store a hashed key, it can change across PostgreSQL major versions.

    Session-level advisory locks: advisory.Lock, advisory.TryLock, advisory.Unlock and the string variants (advisory.LockString, advisory.TryLockString, advisory.UnlockString, which take the same advisory.Hash64 option) take pg_advisory_lock and friends. They need a handle whose statements stay on one connection: db.OnConn(pc) over a connection from Pinner.Pin. A pooled *DB fails with ErrValidation, because the lock and the unlock could reach different connections. The lock lasts until advisory.Unlock or until the connection closes, so unlock before pc.Release() (or Discard the connection if the unlock fails). db.IsPinned() reports whether a handle is pinned.

    Shared advisory locks (the reader half of a reader/writer pair on one key): advisory.XactLockShared, advisory.TryXactLockShared, advisory.LockShared, advisory.TryLockShared, advisory.UnlockShared and the ...String forms take pg_advisory_xact_lock_shared, pg_advisory_lock_shared and friends, with the same arguments, advisory.Hash64 option, transaction and pinned-connection rules as the exclusive helpers. Any number of sessions hold the shared lock of a key together; none runs while another holds the exclusive lock of that key (advisory.XactLock), and the exclusive lock waits for every shared holder. advisory.XactLockSharedString(ctx, tx, k, advisory.Hash64(52)) takes the lock pg_advisory_xact_lock_shared(hashtextextended(k, 52)) takes. advisory.Unlock does not release a shared lock; use advisory.UnlockShared.

    Typed expressions (no momo.SQL needed). Computed values (momo.Func and, in the package github.com/azrtydxb/momo/sqlfn, sqlfn.Substr, sqlfn.Lower, sqlfn.Upper, sqlfn.Length, sqlfn.Case, sqlfn.Add/sqlfn.Sub/sqlfn.Mul, sqlfn.Cast, sqlfn.Concat, sqlfn.CoalesceExpr) work in Columns, GroupBy, OrderBy and SetExpr, and carry the comparisons of a column for Where and Having: Eq, Ne, Lt, Le, Gt, Ge, EqExpr and the other ...Expr forms, In, NotIn, Between, IsNull, IsNotNull; plus Asc and Desc. An .As alias belongs in the select list: OrderBy accepts it and orders by the alias name, GroupBy rejects it with ErrValidation. A sqlfn.Case used in both the select list and GroupBy must be built with WhenExpr and ElseExpr from literal or column expressions: bound When and Else values get a different $n in each place, and PostgreSQL rejects the mismatch. Otherwise group by position or alias in an outer query. Keyset pagination with After and a per-parent LoadPerParentLimit also reject an alias order key with ErrValidation, because an alias is not valid in WHERE or inside a window ORDER BY; order by the expression itself there.

    A predicate orders through momo.OrderByPredicate(p), which has Asc() and Desc() and renders ORDER BY (p): OrderBy(momo.OrderByPredicate(t.BuiltinKey.IsNull()).Asc(), t.Name.Asc()) lists rows with a builtin_key first. False sorts before true, so (col IS NULL) ASC puts NULLs last on every dialect. A predicate has no Asc method of its own, because Predicate is an interface. NullsFirst and NullsLast on it are ErrUnsupported on MySQL and MariaDB. After over a predicate key is ErrValidation, and so is a predicate in the outer OrderBy of a SelectUnion (unqualified result columns only). OrderByPredicate(nil) is ErrValidation; an agg call's OrderBy needs .Asc() or .Desc().

    Joined and CTE-prefixed writes:

    • UpdateQuery.From(src) renders UPDATE t SET ... FROM src WHERE ... and DeleteQuery.Using(src) renders DELETE FROM t USING src WHERE .... src is a table, aliased table, momo.CTE(name) or momo.FromSubquery(q, alias), as in a join; reference its columns with momo.ColumnOf or the model's columns, join it to the target in Where, and assign from it with col.SetExpr(srcCol). The soft-delete filter and interceptors do not apply to src: add that predicate to Where. MySQL and MariaDB render the multi-table forms (UPDATE t, src SET t.col = ..., DELETE t FROM t, src WHERE ...); SQLite has UPDATE ... FROM (3.33 or later) but no DELETE ... USING (ErrUnsupported).
    • With From or Using the unfiltered-mutation guard is stricter: at least one Where predicate must reference a column of the target table, otherwise the statement joins every target row to the source and fails with ErrUnfilteredMutation unless AllRows() confirms it. A condition only on the source, or a raw momo.SQL fragment, does not count. An Or counts only when every branch references the target (one branch off the target can be true on its own, which touches every target row); an And counts when any term does. momo.Not swaps the rules (a negated And needs every term on the target, a negated Or any term), and momo.JoinSQL with AND or OR follows the same rules as And and Or. The guard checks that Where references the target, not that it restricts it: a constant-true predicate such as t.id = t.id passes. From cannot be combined with BulkUpdate (ErrValidation), and RETURNING with From works on PostgreSQL and SQLite only.
    • From and Using take more than one source (From(momo.CTE("due"), otherTable)), rendered as a comma list. With two or more sources the guard applies the same rule to each source: a source that no Where predicate references is cross-joined, and the statement is ErrUnfilteredMutation unless AllRows() confirms it. One source is checked against the target only.
    • Returning accepts columns of a From or Using source or CTE (momo.ColumnOf, or a table's descriptors under its alias). On PostgreSQL a statement with a source renders its whole RETURNING list qualified, so a column the source shares with the target is not ambiguous. Read such a list with momo.ScanUpdate or momo.ScanDelete, which scan into a plain struct, projection or tuple row by result column name (s.url is url; two returned columns with the same name are ErrValidation). Rows and One refuse a source column (ErrValidation), since the model has no field for it. SQLite's RETURNING reads the modified table only, so a source column there is ErrUnsupported.
    • UpdateQuery.With and UpdateQuery.WithRecursive exist on UpdateQuery, DeleteQuery and InsertQuery, with the SelectQuery signature. PostgreSQL and SQLite render the WITH before the statement; MySQL accepts it before UPDATE and DELETE only (ErrUnsupported before INSERT), and MariaDB refuses it there too (ErrUnsupported, not verified). A WITH on a bulk insert that would split into chunks at the parameter limit is ErrValidation, and a UpdateQuery.With combined with BulkUpdate is ErrValidation.
    • InsertQuery, UpdateQuery and DeleteQuery with Returning are Subquery values, usable as the body of SelectQuery.With on any statement: a select with .With("x", ins).From(momo.CTE("x")) renders WITH x AS (INSERT ... RETURNING ...) SELECT ... FROM x. PostgreSQL has data-modifying CTEs; SQLite and MySQL return ErrUnsupported. A DML body needs Returning only when the outer statement reads the CTE; a body that nothing reads (WITH d AS (DELETE ...) INSERT ...) builds without it, and PostgreSQL reports the error if it is read. A DML body renders with the handle's interceptors (with a background context) but runs no model hooks and no beforeWrite check; the outer statement's Exec or All is what executes it. An INSERT body is never chunked: one that binds more parameters than the dialect allows fails with ErrLimitExceeded.

    Bulk and set-based writes (PostgreSQL):

    • InsertQuery[T].Copy streams models through the driver COPY path. It returns ErrUnsupported on SQLite and MySQL and through FromSQLDB (the driver must offer a COPY path). It runs the insert interceptors (deny only, a predicate they add is ignored) and the BeforeInsert hook over a copy of the models, validates fields like Models, and counts as a write for NewUnitOfWork. It skips OnConflict, Returning and chunking, and it cannot be combined with Model, Models, InsertQuery.Values, FromSelect, OnConflict or Upsert (ErrValidation). On a *DB with WithImplicitTx it runs in its own transaction, so WithTxSetup applies; on a pinned OnConn handle with WithTxSetup it fails closed with ErrUnsupported.
    • InsertQuery[T].Unnest() (the method, not the package-level FROM source momo.Unnest) renders a Model or Models insert as INSERT ... SELECT * FROM unnest($1::bigint[], $2::text[]): one array parameter per written column, one statement. The bind count does not depend on the row count, so it bypasses MaxParams and WithMaxParams and never chunks (and is not split into a transaction of several statements). Other dialects return ErrUnsupported. InsertQuery.Values, InsertQuery.ValuesRows and FromSelect return ErrValidation, and so does a model without a table schema in its generated metadata (the array types come from it). Int, float, bool, string, time.Time and []byte columns bind as typed slices ([]*T when a value is NULL); any other element type (uuid, json, decimal, named enums) falls back to []any, which pgx may reject for an array type, so use plain Models for such a model. rows, err := momo.Query[momo.Row2[int64, string]](ctx, q, `SELECT id, title FROM tasks WHERE done = ?`, true)
for row, err := range momo.QueryRows[momo.Row2[int64, string]](ctx, q, `SELECT id, title FROM tasks`) { _, _ = row, err }
// Helpers: momo.In(slice) (empty slice is a build error), momo.Ident("col"), momo.RawSubquery(sql, args...)
    • DON'T build SQL text with fmt.Sprintf from user input. Use ?, In, Ident.
    • QUALIFY column names in raw fragments inside joined or preloaded queries ("tasks"."title"): Momo qualifies its own columns, and an unqualified name becomes ambiguous with a joined table. A column qualified by a table that is not in the statement's FROM/JOIN is ErrValidation at build time.
    • On PostgreSQL write ? | with a space for a bind followed by OR; ?| and ?& are operators. On PostgreSQL a fragment may use native $n placeholders instead (see "Porting pgx and sqlc SQL" below); do not mix them with ?/@name.
    • Returned results of raw queries bypass soft-delete, hooks and timestamps.
    • Query[T] (buffered, []T) and QueryRows[T] (streaming iter.Seq2[T, error]) are the multi-column raw read, for a hand-written SELECT or ... RETURNING. T is Row1..Row10 (positional: the result must have exactly that many columns) or a model or projection (matched by column name in any order, exact then case-insensitive; an unmapped, missing or duplicated result column is ErrValidation). T may also be a plain struct with no generated metadata (no generator run, any number of columns): its exported fields are the columns, named by a momo:"column:x" tag or else the column name the DB's naming preset gives the field (momo.New(drv, momo.WithNaming(naming.Prisma{})); snake_case without the option: UserID is user_id, RoleIDs is role_ids, HTTPServer is http_server), momo:"-" skips a field, the fields of an embedded struct count as the outer struct's own (unless it is a time.Time, a sql.Scanner or has a column tag; an outer field shadows an embedded one, two fields on one column and an embedding cycle are ErrValidation; an embedded pointer struct is allocated for every row and stays non-nil even when all of its columns are NULL), and a pointer field receives NULL as nil (NULL into a non-pointer field is the driver's scan error). Names compare exactly, then case-insensitively. The reflection plan is built once per type and cached (BenchmarkQueryPlainStruct). A type with generated metadata (a model, a projection, Row1..Row10) always uses it, and a type that is neither is ErrValidation before the statement runs. By-name matching needs every result column to map to a field and every field to be in the result (the error names the column or field), so SELECT d.*, count(*) needs a struct with a field for each result column. Placeholders, hooks (op raw), error classification and argument redaction are those of Exec; interceptors, soft-delete filters and AfterLoad do not apply to raw SQL. QueryRows closes the cursor on early break, on an error and on a canceled context (ErrCanceled).
    • RawRows(ctx, q, sql, args...) returns the open cursor (momo.ColumnRows: Next, Scan(dest...), Columns, Err, Close) for a result whose shape is only known at run time. It has the hooks (op raw), WithTxSetup, error classification and redaction of Query, on a *DB, *Tx or AdoptTx handle. Always close it: an unclosed cursor holds its connection (and, under WithImplicitTx, its transaction). A canceled context closes it and Err is ErrCanceled (also when the cancel came after the last row, as in QueryRows). Under WithImplicitTx raw SQL counts as a write: reading to the end commits, and a Close before the end (even with no Next), after a Scan or driver error, or after a cancel rolls back and returns ErrValidation; without it an early Close is plain. Scan errors are classified and recorded on the hook event. Columns is the driver's list: empty means no columns (an UPDATE without RETURNING) or an unnamed driver. Prefer Query[T] when the shape is known.

    Porting pgx and sqlc SQL¶

    On the PostgreSQL dialect, raw SQL (Exec, Scalars, Query, QueryRows, SQL, TypedSQL, RawSubquery) accepts PostgreSQL's native $1, $2, ... placeholders, so a statement written for pgx or sqlc moves over unchanged:

    // pgx / sqlc:   pool.Exec(ctx, "UPDATE tasks SET done = $1 WHERE owner = $2 OR creator = $2", true, uid)
affected, err := momo.Exec(ctx, q, "UPDATE tasks SET done = $1 WHERE owner = $2 OR creator = $2", true, uid)

    Rules:

    • $n binds positional argument n of that call. A reused $n (here $2) binds the argument once. An In, Ident or Expr argument is rendered again at each use. Momo renumbers: inside a larger statement (TypedSQL or RawSubquery after earlier Where binds) $1 still means the fragment's first argument.
    • One style per fragment. Mixing $n with ?, @name or Named is ErrValidation.
    • Every $n needs an argument ($3 with two arguments, or $0, is ErrValidation) and every argument must be used (a gap such as $1, $3 is ErrValidation), so a typo fails at build time.
    • A $n inside a string literal, quoted identifier, comment or dollar-quoted body is text, not a placeholder.
    • Other dialects: $n is ErrUnsupported at build time on SQLite and MySQL, even when the fragment has no ?. Port such statements to ? (or @name) when the code must run on SQLite or MySQL.
    • A literal $n that must reach the server as text, as in PREPARE or a CREATE FUNCTION body that refers to its parameters, is read as a placeholder and fails with ErrValidation for a missing argument. Put it where momo treats it as text: inside a string literal or a dollar-quoted body, for example DO $$ BEGIN EXECUTE 'PREPARE p AS SELECT $1::int'; END $$.
    • Behaviour change: before native $n support a $1 in raw PostgreSQL SQL went to the server untouched. It is now a momo placeholder, so a statement that used $1 as text needs the treatment above.
    • sqlc sqlc.arg(name) / @name styles: use momo.Named("name", v) with @name.
    • Typed casts keep working: $1::int is fine.

    SelectQuery.SQL() returns Compiled{SQL, Args} without running. Explain(ctx) runs EXPLAIN (never ANALYZE) and returns plan text; it binds parameters and does not execute the query. Inside a Tx, it sees that transaction's settings. momo.Explain(ctx, q, compiled) plans any statement's Compiled (writes included, PostgreSQL, SQLite, MySQL and MariaDB) and momo.ExplainAnalyze(ctx, q, compiled) runs it under EXPLAIN ANALYZE (PostgreSQL only; always rolled back, but a rollback cannot undo nextval, NOTIFY or dblink effects). Momo never calls either on its own; see observability.

    Select-time guards: Limit/Offset negative is ErrValidation.

    Writing your own expression¶

    Code outside the root package (your own package, or a Momo subpackage) builds typed expressions with a small extension API. Every name below is an extension point: writing one correctly means identifiers go through Builder.Ident and values through Builder.Arg or Builder.ArgFor, never concatenated into the SQL.

    • momo.Ops[T]: embed it in your struct to make the struct an Expression[T] (a Predicate when T is bool) with Eq, Ne, Lt, Le, Gt, Ge, IsNull, IsNotNull, Between, In, NotIn, Asc and Desc.
    • momo.NewOps[T]: binds the embedded Ops to the finished struct. Call it in the constructor, as the example below does. An unbound Ops fails the build with ErrValidation.
    • momo.Typed[T]: wraps any Expr as an Expression[T] without comparison methods.
    • momo.PredicateFunc: turns func(*momo.Builder) into a Predicate.
    • momo.Flagged and momo.FlagsOf: the column flags of an expression, or 0. Give your expression a Flags() uint16 method that returns FlagsOf of the wrapped column so a sensitive column stays masked.
    • Builder.ArgFor: binds a value, masked as momo.RedactedArg in hook events when the flags argument has FlagSensitive.
    • Builder.RenderSensitive: renders an expression and returns the flags with FlagSensitive added when it read a sensitive column; pass the result to the other operands.
    • Builder.ExprFor: renders an expression with every argument it binds masked when the flags argument has FlagSensitive.
    • Builder.Unsupported: records ErrUnsupported for a dialect that cannot express the feature. Builder.WriteByte appends a trusted SQL byte.
    • Order.AppendOrder: renders one ORDER BY item (expr ASC|DESC [NULLS ...]) for an expression that carries its own ordering, such as agg.Call.OrderBy.
    • Builder.AppendFilter: writes FILTER (WHERE p) after an aggregate call and fails the build for a nil predicate or on MySQL.
    • momo.WindowOf[T]: turns your aggregate call into a window function, call OVER (...); agg.Call.Over is built on it.
    • Builder.MarkSensitive: call it from an expression that writes a sensitive column's identifier directly, so an enclosing comparison masks its other operands. A column reference does this by itself.
    • momo.ValidName: checks a function name or alias before you write it with Builder.Ident.
    • momo.VectorColumnOf: the VectorColumn behind any VectorSource (read its table, name, dimension and flags for a custom distance expression).
    package main

import (
    "fmt"

    "github.com/azrtydxb/momo"
)

type shout struct {
    momo.Ops[string]
    src momo.Expr
}

func newShout(src momo.Expr) shout {
    s := shout{src: src}
    s.Ops = momo.NewOps[string](s)
    return s
}

func (s shout) AppendSQL(b *momo.Builder) {
    b.WriteString("upper(")
    s.src.AppendSQL(b)
    b.WriteString(")")
}

func (s shout) Flags() uint16 { return momo.FlagsOf(s.src) }

// newShout(col) works in Columns, Where (newShout(col).Eq("X")) and OrderBy.
func main() {
    title := momo.NewColumn[string]("documents", "title", 0)
    _ = newShout(title).Eq("X")
    fmt.Println("ok")
}

    7. Transactions¶

    err := db.Tx(ctx, momo.TxOptions{}, func(tx *momo.Tx) error {
    // use tx (a momo.Querier), NOT db, for everything in here
    if _, err := momo.Update[models.Account](tx).
        Set(account.Balance.SetExpr(momo.TypedSQL[int64]("balance + ?", amt))).
        Where(account.Owner.Eq(to)).Exec(ctx); err != nil {
        return err // any error (or panic) rolls back
    }
    return nil // nil commits
})
    • db.Tx(ctx, opts, fn) commits on nil, rolls back on error or panic. fn runs exactly once; Momo never retries it.
    • DON'T use db inside the closure: it runs outside the transaction on another connection and can deadlock on a small pool.
    • TxOptions{ReadOnly: true} makes the server refuse writes (SQLSTATE 25006; Momo has no sentinel for it: errors.As(err, &pgErr) with *pgconn.PgError). TxOptions{Isolation: sql.LevelSerializable} sets the level; supported: read uncommitted, read committed, repeatable read, serializable. Any other level is ErrUnsupported.
    • Savepoints: tx.Tx(ctx, func(sp *momo.Tx) error {...}) runs in a savepoint; if it fails only its work is undone and the outer transaction continues. Without a savepoint PostgreSQL aborts the whole transaction at the first error. Manual: tx.Savepoint(ctx, name), tx.RollbackTo(ctx, name), tx.Release(ctx, name).
    • Manual control: tx, err := db.Begin(ctx, opts), tx.Commit(ctx), tx.Rollback(ctx); a finished *Tx returns ErrTxDone. Prefer db.Tx.
    • Incremental adoption in a database/sql or pgx codebase, both directions:
    • Adopt a transaction the caller began: mtx := db.AdoptTx(pgxdriver.SQLTx(sqlTx)) for a *sql.Tx (database must be pgx-stdlib backed, FromSQLDB), or db.AdoptTx(pgxdriver.PgxTx(pgxTx, opts...)) for a pgx.Tx (pgxpool driver; opts are the options of New, such as WithExecMode; an unsupported exec mode returns ErrUnsupported on use, as with New). An adopted pgx.Tx keeps Batch and COPY; an adopted *sql.Tx has neither. Statements, hooks, error classification and savepoints (mtx.Tx) work as usual. Commit and Rollback on mtx return ErrAdoptedTx and do nothing: the caller commits or rolls back its own transaction. After that, mtx statements return ErrTxDone. A nil argument panics.
    • Expose the handle behind a *Tx to legacy helpers: pgxdriver.UnwrapSQLTx(tx) returns (*sql.Tx, bool) and pgxdriver.UnwrapPgxTx(tx) returns (pgx.Tx, bool); false when the Tx belongs to the other driver kind. Works for db.Tx callbacks, adopted transactions and savepoint scopes (the outer transaction). Finish a momo-begun transaction through momo, never through the unwrapped handle.
    • Mixing is safe: a legacy SELECT ... FOR UPDATE helper and momo statements can alternate on the same transaction.
    • Do not call blocking network I/O inside fn.
    • Retry the WHOLE db.Tx on ErrSerialization (PostgreSQL 40001 serialization failure and 40P01 deadlock). Only when fn has no side effects outside the database. Copy of examples/transactions:
    func retrySerializable(ctx context.Context, db *momo.DB, fn func(tx *momo.Tx) error) error {
    const (
        maxAttempts = 3
        backoff     = 20 * time.Millisecond // doubles in a real service
    )
    var err error
    for attempt := 1; attempt <= maxAttempts; attempt++ {
        err = db.Tx(ctx, momo.TxOptions{Isolation: sql.LevelSerializable}, fn)
        if !errors.Is(err, momo.ErrSerialization) {
            return err
        }
        if attempt == maxAttempts {
            break // out of attempts: return the error without sleeping
        }
        d := backoff/2 + rand.N(backoff) // math/rand/v2: jitter so competitors do not collide in lockstep
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-time.After(d):
        }
    }
    return err
}
    • On a pinned connection (db.OnConn(pc)) transactions are not available: Begin, Tx, Replace, CreateGraph return ErrUnsupported.
    • Several momo helpers open their own transaction on a *DB and a savepoint on a *Tx: Replace, CreateGraph, chunked InsertQuery.Models, vecsearch.With.

    Rules and limits:

    • Load/LoadAll/Preload clear the association first, so a parent with no children is empty (nil), never stale. NULL-key parents get an empty association. Parent order never changes.
    • Scope(...) and Then(...) combine: both return a RelationLoader with Scope and Then methods, so document.Comments.Scope(approvedOnly).Then(comment.Author) (with approvedOnly a momo.LoadWhere[models.Comment] option) filters the comments and loads each one's author in one loader. The options apply to that relation's children only; nested loaders carry their own; the nested level runs over the surviving children only (one statement per level).
    • Joined() is belongs-to only, and only when the child key is the child's primary key or a single unique column. Has-one, has-many, many-to-many give ErrUnsupported. momo.Load(ctx, db, docs, X.Joined()) does not compile (Joined() returns a Loader, Load wants a Relation; cannot infer C), and LoadAll returns ErrUnsupported. Also ErrUnsupported with Then, GroupBy, Having, ForUpdate, Each, Iter. With Columns the select list must have one expression per mapped field (ErrValidation). Qualify raw column names in the parent's Where (ambiguity with the joined table).
    • LoadPerParentLimit(n): has-many and many-to-many only (belongs-to and has-one ErrUnsupported); n < 0 is ErrValidation; 0 is unlimited. LoadWhere filters before the limit.
    • Has/HasNo predicates must name the child column through the alias momo_r: comment.Approved.As("momo_r").Eq(true); an unaliased column refers to the OUTER table. Has/HasNo nest: each level has its own child alias (momo_r, momo_r2, momo_r3; join table momo_j, momo_j2), the inner one correlates on the enclosing alias, and As("momo_r") in a scope always means that scope's own level. As(momo.RelAlias(n)) names level n explicitly (1 is the outermost) and is never rewritten. A nested Has in a self-reference correlates on the enclosing child; HasFrom(alias) keeps the alias given. Do not name your own aliases momo_r<N> or momo_j<N>.
    • Has-one that matches several children for a parent: ErrTooManyRows.
    • Link, Unlink, Replace, Count write SQL directly: model hooks, field hooks and UpdatedAt are NOT run. Use the model's update path when those must run. They never modify the values you pass.
    • Many-to-many Link relies on a primary or unique key over the join columns. Join tables generated from many2many tags have one. A hand-written join table needs a unique key, or Link inserts duplicates.
    • Has-one/has-many Unlink and Replace clear the foreign key: it must be nullable, else ErrNotNullViolation. Delete the children instead if they cannot exist without a parent.
    • Belongs-to is not linkable: all four helpers return ErrUnsupported. Set the foreign key field on the parent and Update it.
    • NULL parent key (or NULL child key on many-to-many) is ErrValidation for Link/Unlink/Replace; Count returns 0. Link/Unlink with no children are no-ops.
    • Replace is a transaction (*DB) or savepoint (*Tx) and locks the parent row (FOR UPDATE), so concurrent Replace on one parent serialize. Link/Unlink take no lock and may interleave. On a *Tx the lock lasts until your transaction ends. A non-existent parent locks nothing.
    • Link/Unlink needing several chunks are atomic on a *DB (one transaction); on a *Tx a later chunk failing leaves earlier chunks applied until you roll back.
    • CreateGraph: one level deep; always INSERTs (never matches existing rows); belongs-to children first, has-one/has-many after the parent, many-to-many children inserted then linked; hooks, timestamps and defaults run. On a *Tx it runs in a savepoint. Nil parent, a model as its own child, or a NULL key that must be copied: ErrValidation. Has-many and many-to-many children go in as chunked bulk inserts (1000 children = one statement). A dialect without RETURNING gives ErrUnsupported before a transaction opens. DON'T list a many-to-many relation whose children are already stored: they are inserted again and fail with ErrUniqueViolation; use Link for existing rows.
    • FindOrCreate needs a UNIQUE constraint on exactly the key columns. It overwrites your struct with the stored row when it exists; a soft-deleted row is not found, it fails with ErrUniqueViolation. Under REPEATABLE READ/SERIALIZABLE the re-select can return ErrNotFound: retry the transaction. Empty key or unmapped column: ErrValidation.
    • Tag-declared relations: belongs_to needs a single-column primary key on its target (the referencing model may have a composite key containing the fk column); has_one/has_many need one on the parent; many2many on both.
    • A pipelined load buffers a whole level's child rows (about twice the memory of sequential). An unscoped load of a huge has-many is expensive: scope it.
    • Many-to-many to self and join tables with extra columns are not supported by tag; use an explicit join model struct for extra columns.
    • Parent keys are chunked under the bind limit automatically; WithMaxParams(n) lowers it for tests.

    The distance builders live in package github.com/azrtydxb/momo/vecop. A pointer field (*vector.Vector) is nullable (momo.NullVectorColumn).     Index rules (MomoConfig; validated by the generator, error wraps schema.ErrInvalidVectorIndex):

    Method Types Max dim for index Opclass <type>_<x>_ops, x in
    hnsw vector, halfvec, sparsevec, bit vector 2000, halfvec 4000, bit 64000 l2, ip, cosine, l1; bit: hamming, jaccard

    • A vector column above 2000 dims cannot have an ANN index; store it as vector.HalfVector (up to 4000 for an index).
    • Dimensionless columns: a vector.Vector or vector.HalfVector field without dim maps to bare vector or halfvec and holds embeddings of any size (NovaCRM KbChunk.embedding). Its descriptor has Dim() zero, so a distance argument of any size is accepted and still checked for NaN and Inf. Store a dims column and always filter on it before ordering by distance, since pgvector errors when it compares two sizes. hnsw and ivfflat on such a column are refused (error wraps schema.ErrInvalidVectorIndex, names the column), as are expression parts; it is searched by sequential scan.
    • hnsw params: m 2..100 (16), ef_construction 4..1000 (64, at least 2*m). ivfflat REQUIRES IndexOpts.With("lists", "N") (1..32768).
    • An index covers one plain column; expression parts are rejected.
    • Index opclass must match the distance function: vector_cosine_ops with vecop.Cosine, vector_l2_ops with vecop.L2, vector_ip_ops with vecop.InnerProduct, vector_l1_ops with vecop.L1. A mismatch silently runs a sequential scan.

    • Hit is a projection (section 4); the generator emits its meta. The select list is positional, so the field name Distance only labels the computed column.
    • A vector literal is vector.Vector{0.1, 0.2, 0.3} (vector.Vector is []float32; its length must equal dim).
    • vecop.InnerProduct is pgvector <#>: the NEGATIVE inner product, so ascending order is closest.
    • Vector columns have no Lt/Le/Gt/Ge/Between; use a distance builder.
    • Passing a dense vector to a bit builder (or the reverse) does not compile.
    • Where only narrows candidates; it never reorders.
    • Order a vector search by the distance alone. Adding a tie-break key such as item.ID.Asc() makes PostgreSQL sort on top of the index scan, and on some versions (seen on PostgreSQL 16) the planner then skips the HNSW or IVFFlat index entirely. Order among equal distances is unspecified. Check the plan with Explain (see vector-search).

Zero leaves the server default. Out of range: ErrValidation. Iterative/max-scan/scan-mem/max-probes fields on pgvector older than 0.8.0 or a missing extension: ErrUnsupported.

    Pitfalls:

    • JSON extraction in GROUP BY: a key that is not plain letters, digits and underscores is a bound parameter, and PostgreSQL treats the parameter in the select list and the one in GROUP BY as different expressions and rejects the query. Plain keys are inlined and group fine, except on a sensitive column, whose keys are always bound so they stay masked; for those and any other key group on a SQL fragment with a literal key. Inlined keys vary the statement text per key, so pass only keys from a fixed set, not user input.
    • Filtered search: with iterative scan off, an ANN index returns its nearest candidates and applies Where afterwards, so a selective filter can return FEWER than Limit rows even when enough match. Set HNSWIterativeScan (vecsearch.IterativeRelaxedOrder; results stay approximate and can still be short when the filter matches fewer rows than HNSWMaxScanTuples).
    • Small-table seq scan: below a few thousand rows the planner prefers a sequential scan, so Explain shows no index use in tests. That is correct. To check index use on a small table, run in a transaction: tx.SetLocal(ctx, "enable_seqscan", "off") then query.Explain(ctx) and look for the index name. Tx.SetLocal(ctx, name, value) sets any run-time parameter; never pass an untrusted name.
    • Opclass mismatch or missing opclass for hnsw: see above.
    • Index-less exact search (ExactSearch) is for measuring recall or small tables.
    • Binary wire codec is opt-in (pgxdriver.ConfigureVectors(cfg) before pgxpool.NewWithConfig, then pgxdriver.WithVectorFormat(pgxdriver.VectorBinary) with a describe-based exec mode). Default text transport is correct; skip unless profiling says otherwise. NewPool does not call ConfigureVectors.
    • Reciprocal-rank-fusion hybrid search is momo.HybridSearch (PostgreSQL only, vectors.md); for a custom mix, combine a distance and a text rank in one score (fulltext.md).

    Details: vectors.md. Example: vector-search.

    10. Errors¶

    Momo errors are *momo.Error{Kind, Op, Table, Column, Constraint, Err}. Check with errors.Is(err, momo.ErrX) (matches momo.Error.Kind) and reach the driver error with errors.As (for example *pgconn.PgError). e.Detail() returns the raw driver detail (for PostgreSQL the key text) that Error() hides. Detail() is unmasked and can quote sensitive values: never log it or return it to a client. Never string-match error text.

    switch {
case errors.Is(err, momo.ErrNotFound):
case errors.Is(err, momo.ErrUniqueViolation):
    var me *momo.Error
    if errors.As(err, &me) { _ = me.Constraint } // which constraint
}

    me.Column is empty for unique, foreign-key and check violations (PostgreSQL reports a column only for NOT NULL). Use Constraint for those three.

    Error When What to do
    ErrNotFound One, First, UpdateQuery.Model, DeleteQuery.Model matched no row; FindOrCreate re-select miss. All/Each/Iter never return it map to 404 or create
    ErrTooManyRows One matched more than one row; has-one load matched several children fix the filter or the data
    ErrUniqueViolation unique key or primary key violated (SQLSTATE 23505) conflict; Constraint names it
    ErrForeignKeyViolation FK violated (23503) missing parent or children still exist
    ErrCheckViolation CHECK failed (23514) business rule
    ErrNotNullViolation NULL into NOT NULL (23502); has-one/has-many Unlink/Replace on a NOT NULL FK fix the data or nullability
    ErrSerialization serialization failure or deadlock (40001, 40P01) retry the whole transaction with backoff
    ErrBusy lock not available (55P03) retry later
    ErrOptimisticLock UpdateQuery.Model on a versioned model with a stale version reload, reapply, retry
    ErrUnfilteredMutation Update/Delete without Where and without AllRows() add a filter
    ErrValidation bad input detected before the database: wrong vector dim, After count, empty Models, writing a reserved/read-only column, plain Delete on a soft-delete model, negative Limit, Link with NULL key, bad vecsearch.Settings, qualifier not in FROM programmer or input error; fix the call
    ErrUnsupported dialect or driver cannot do it: Each/Iter with Preload; Joined shape; LoadPerParentLimit on to-one; belongs-to helpers; keyset on nullable key; IndexedBy; iterative search on pgvector < 0.8; simple protocol exec mode; non-standard isolation; transactions on a pinned conn; SQLite/MySQL redesign the call; not retryable
    ErrAdoptedTx Commit or Rollback on a *Tx from AdoptTx; the caller owns that transaction finish the transaction with the caller's own handle
    ErrTxDone *Tx already committed or rolled back do not reuse a finished Tx
    ErrLimitExceeded configured limit exceeded (for example one row has more columns than the bind limit) split or raise the limit
    ErrPinnedBusy Release on a pinned connection that is still executing wait and release again
    ErrInvalidVector a vector value failed validation (same value as vector.ErrInvalidVector) fix the vector

    Driver errors Momo does not classify keep their original type: reach them with errors.As(err, &pgErr). Data exceptions (SQLSTATE class 22, for example invalid text representation) hide the message because it may quote the value; the *pgconn.PgError is still reachable.

    Migration errors (package migrate and the CLI, exit codes in section 5): migrate.ErrChecksumMismatch, migrate.ErrDirty, migrate.ErrLocked, migrate.ErrDestructive, migrate.ErrBranchConflict, migrate.ErrStagedRequired, migrate.ErrBaselineMismatch, migrate.ErrNoSnapshot, migrate.ErrNoDown; schema.ErrNewerFormat (a snapshot written by a newer momo).

    Rules:

    • DO use errors.Is, not == (errors are wrapped).
    • DON'T retry ErrUnique/ErrValidation/ErrUnsupported; DO retry ErrSerialization (whole transaction) and ErrBusy (with backoff).
    • DON'T return raw *momo.Error text to API clients; it names tables and constraints.

    11. Testing apps that use Momo¶

    Test against a real PostgreSQL with pgvector, not a mock. CI of Momo itself runs pgvector/pgvector:0.8.7-pg16 and 0.8.7-pg17.

    To list or freeze the SQL an app issues without a database, register named builders with momo.RegisterQuery(name, func(q momo.Querier) momo.Compilable) (use momo.RawQuery for hand-written SQL), read them with QueryRegistry.Compile(dialect) and freeze them with momotest.QueryGolden (MOMO_UPDATE_GOLDEN=1 rewrites the files; registering a name twice panics). The SQL of InsertQuery[T].Model depends on the sample model's dbdefault fields (a zero one is left out of the column list), so register it with the fields set as a real call sets them, or register InsertQuery[T].Values with Column.Set for each column or InsertQuery[T].Omit before InsertQuery[T].Model, whose column list does not depend on values (see testing.md).

    Use the public kit github.com/azrtydxb/momo/momotest (see testing.md):

    //go:build integration

db := momotest.New(t, momotest.WithMigrations(app.Migrations()))  // schema per test, dropped after
tx := momotest.NewTx(t, momotest.WithMigrations(app.Migrations())) // rolled back after; Commit refused
momotest.Seed(t, tx, momotest.Insert(&org), momotest.Insert(&user))

    momotest.LoadFixtures(t, q, "fixtures.yaml") inserts a YAML file of table: [rows] in file order (columns sorted, null is NULL, values bound), and sqlitetest.New(t) (package momotest/sqlitetest, cgo) returns a *momo.DB on a throwaway SQLite file per test. momotest.AssertSQL(t, query.SQL(), want) compares compiled SQL ignoring whitespace without running it (the failure never shows an argument value), and momotest.AssertUsesIndex(t, q, compiled, "index_name") fails unless a plain EXPLAIN of the statement reads that index (PostgreSQL and SQLite; the plan can echo literal values, so use test data that is not sensitive). See testing.md.

    It reads MOMO_TEST_POSTGRES_URL (skip when unset, fail when MOMO_REQUIRE_INTEGRATION=1), is safe with t.Parallel and -race, and momotest.WithExtensions("vector") creates the extension first. What it does, if you need to do it by hand (the examples' own harness is internal to the Momo module):

    1. Read an admin URL from an env var (the examples use MOMO_TEST_POSTGRES_URL); t.Skip when it is unset (and t.Fatal when your CI sets a require flag).
    2. Create a scratch database per test (CREATE DATABASE t_<random> over a plain pgx connection), connect pgxdriver.NewPool to it, drop it in t.Cleanup.
    3. Apply your real migrations from code:
    import (
    "github.com/azrtydxb/momo/migrate"
    mpg "github.com/azrtydxb/momo/migrate/postgres"
)

db := momo.New(pgxdriver.New(pool))
e, err := migrate.NewEngine(db.Driver(), os.DirFS("../migrations"), migrate.WithDialect(mpg.New()))
if err != nil { t.Fatal(err) }
if _, err := e.Apply(ctx, migrate.ApplyOptions{}); err != nil { t.Fatal(err) }

    (The role needs permission to CREATE EXTENSION vector.) Pass the migrations directory configured in migrate.dir.postgres. 4. Run the code under test against db; assert on results and on errors.Is. 5. Also run momo generate --check and momo migrate validate as tests or CI steps.

    What to mock and what not:

    • DON'T mock momo.DB, momo.Tx or momo.Querier. Querier is sealed (it has unexported methods; you cannot implement it) and query builders are the code under test.
    • DO hide Momo behind your own repository/service interface and fake THAT in unit tests of business logic.
    • DO test queries, migrations, relations and transactions against real PostgreSQL.
    • Use WithClock(func() time.Time) (momo.New(drv, momo.WithClock(fn))) for deterministic created_at/updated_at/soft-delete times.
    • WithMaxParams(n) with a small n exercises chunking with little data.
    • The momo.Driver interface can be faked, but the mock then proves nothing about SQL; prefer Select...SQL() golden checks for pure SQL-shape tests.

    Examples: every examples/*/example_test.go, harness examples/internal/exampletest.

    Observability and scoping helpers¶

    • momolog.New(logger, opts...) returns a hook that logs one record per statement (op, table, relation, sql, duration, rows, err) and, because it also implements momo.RelationHook, one record per relation load (parent, name, kind, parents, children, queries, duration, err). Options: momolog.Level, momolog.SlowOver (statements slower than the duration log at WARN) and momolog.Values. Argument values are logged only with momolog.Values(true) and momo.WithArgLogging together; a sensitive column's value is momo.RedactedArg.
    • momo.WithQueryScope(ctx) groups statements for momo.NewNPlusOneHook(threshold, report), a development hook that reports once per statement shape per scope when the shape runs more than the threshold. Contexts without a scope are not tracked; a scope tracks at most 1024 shapes; a panic in the report function is recovered. A single batched relation load runs one statement per relation and does not trigger it.
    • Hooks, package github.com/azrtydxb/momo/obs (see observability): both implement momo.Hook and momo.RelationHook, so momo.WithHook registers them for statements and for relation loads. &obs.Recorder{} keeps events for test assertions (Events, SQLs, Relations, Reset). obs.NewNPlusOne(threshold, report) with obs.WithScope(ctx) reports a relation loaded more than the threshold times in one scope (a Load inside a loop; one batched Load stays silent). It is separate from momo.NewNPlusOneHook, which counts repeated statement shapes in a momo.WithQueryScope scope; each needs its own scope on the context. A value bound from a sensitive column is always momo.RedactedArg in what these hooks see. They are safe for concurrent use. For slog use momolog.New. obs.NewSlowQuery(threshold, report, obs.WithPlainExplain(plainDB)) reports each statement slower than the threshold and, only with obs.WithPlainExplain, adds a plain EXPLAIN plan (never ANALYZE; inside a transaction through a savepoint that is rolled back). See observability.
    • momo.WithTenant(ctx, tenant) and momo.TenantFilter(ctx, column) add a column = tenant predicate. This is an application-side convenience and NOT a security boundary. It applies only where you add it to a Where: not to Update or Delete, not to the tenant column of an Insert, not to Preload, Load or LoadCounts, joins, subqueries or raw SQL. A missing tenant, or one whose Go type is not exactly the column type, fails the build with ErrValidation (also under Not and Or). The zero value is a real tenant. Enforce isolation with PostgreSQL row-level security: it is configured by your own WithTxSetup function, which reads whatever your code put in the context. To drive both from WithTenant, read the tenant there and call SetConfigLocal. Without WithImplicitTx, non-transactional queries get no setting.
    • WithImplicitTx and RETURNING writes: on an unpinned *DB configured with WithImplicitTx, read the rows of Insert, Update or Delete with Rows to the end (for rows.Next() {}) before Close. A write whose rows were closed unread, or after only the first row, is rolled back and Close returns ErrValidation. This also holds for a panic that unwinds through the loop, however Close is deferred. The library's own single-row helpers (FindOrCreate, UpsertByPK, CreateGraph) read to the end themselves. Handles without WithImplicitTx, Tx and pinned OnConn handles are unaffected.

    12. Rules for AI agents¶

    1. v0.7.0 is PostgreSQL + pgvector via pgx first; the other databases, their drivers and the dialects momo migrate runs are in the generated status near the top of this guide and in docs/capabilities.md.
    2. Install the CLI at the same version as the library (go install github.com/azrtydxb/momo/cmd/momo@v0.7.0).
    3. Models embed momo.Model by value with momo:"table:<name>"; run momo generate after every model change and commit the generated files.
    4. Never edit *_gen.go. Never hand-write MomoMeta for a table model or a projection.
    5. Non-pointer field = NOT NULL; pointer = NULL-able. Use SetNull() only on pointer fields.
    6. Use InsertQuery.Model to store the struct as-is (zeros included); InsertQuery.Values to fall back to database defaults. Use Returning(...).Rows to read identities.
    7. Use UpdateQuery.Set(col.Set(v)) for partial updates, UpdateQuery.Model for whole-row updates with a version column; handle ErrOptimisticLock by reload and retry. UpdateQuery.Set updates do not touch the version.
    8. Never call AllRows() to get past ErrUnfilteredMutation; add a Where.
    9. Soft-delete models: SoftDelete/ForceDelete, not Delete. Raw SQL and projections whose From is a subquery or a hand-built TableRef do not get the soft-delete filter: add Where(<table>.DeletedAt.IsNull()) yourself. A projection read From a generated table (Select[Card], the vector Hit) is filtered automatically; do not add the predicate.
    10. Page with OrderBy + After and a unique tie-break; pass one value per effective ORDER BY key (primary key included).
    11. Pass user input only as arguments to momo.SQL/TypedSQL/Exec/Scalars/Query/QueryRows; qualify column names in raw fragments inside joins.
    12. Inside db.Tx, use only the tx handle. Retry the whole transaction on ErrSerialization with jittered backoff; never retry inside it.
    13. Check errors with errors.Is against the momo.Err* sentinels.
    14. Load relations explicitly (Load, LoadAll, Preload); never assume a field is populated. Scope and Then chain on one relation: rel.Scope(opts...).Then(nested...).
    15. Joined() is belongs-to only; Link/Unlink/Replace/Count are not for belongs-to; helpers skip hooks and UpdatedAt.
    16. FindOrCreate and OnConflict need a matching UNIQUE constraint; many-to-many join tables need a unique key. A partial unique index needs OnConflict(cols).Where(indexPredicate); a conditional DO UPDATE uses .DoUpdate(...).Where(...).
    17. Vector columns take dim:<n>; leave it off a vector or halfvec field only for a dimensionless column (embedding size depends on the model, rows filtered by a dims column; no hnsw/ivfflat index on it). An hnsw index needs an explicit opclass, and any index opclass must match the distance function used in queries (ivfflat on vector defaults to L2); ivfflat needs lists.
    18. Run vector queries that need tuning inside vecsearch.With and use tx there; use iterative scan for filtered ANN searches; expect seq scans on small tables.
    19. Migrations: diff, review SQL, commit all files, apply. Never edit an applied migration; undo with a new one (momo migrate rollback needs a hand-written .down.sql). Run momo migrate lint in CI.
    20. NOT NULL additions without a default: diff --stage, apply, backfill, check no NULLs remain, then diff --enforce-not-null (or give the column a default).
    21. Declare Concurrently() on large-table indexes. -- momo:destructive is informational; only diff --allow-destructive guards drops.
    22. CI must run momo generate --check, momo migrate validate and the diff ci_probe | grep -qx 'no changes' probe; apply also refuses forks and out-of-order versions, but fail the pull request earlier.
    23. Run momo migrate over a direct connection, URL from the environment, never --url (or --url - for stdin). Use sslmode=verify-full for remote databases.
    24. Behind PgBouncer keep the default exec mode; never select the simple protocol.
    25. Test against real PostgreSQL with pgvector; do not mock momo.Querier.
