    Capabilities

    What Momo supports, per database. The status of each database and the dialect flags below are generated from the code: see MySQL and MariaDB, migrations and vectors for the details behind them.

    A database is usable when a driver package for it exists under driver/:

    • PostgreSQL: usable through driver/pgxdriver (vector builders: yes). Migrations: migrate/postgres, run by momo migrate.
    • SQLite: usable through driver/sqlitedriver (needs cgo, not on Windows, vector builders: yes) and driver/sqlitepure (vector builders: no). Migrations: migrate/sqlite, library only (momo migrate does not select it).
    • MySQL and MariaDB: usable through driver/mysqldriver (vector storage and builders depend on the server version). Migrations: migrate/mysql, library only (momo migrate does not select it).

    Legend: yes = implemented for PostgreSQL and covered by the integration suite (make test-integration-postgres, which also runs every dialect-neutral test on SQLite through testopen.Each). no = not provided. ErrUnsupported = the call exists and fails with momo.ErrUnsupported.

    Getting connected¶

    Imports: github.com/azrtydxb/momo (core), github.com/azrtydxb/momo/driver/pgxdriver (PostgreSQL driver), github.com/azrtydxb/momo/vector for vector types and github.com/azrtydxb/momo/vecop for the vector distance builders.

    Open a pool and wrap it, as the README does (the caller closes the pool):

    pool, err := pgxdriver.NewPool(ctx, url) // (ctx, string) (*pgxpool.Pool, error)
if err != nil { return err }
defer pool.Close()
db := momo.New(pgxdriver.New(pool)) // New(pool, opts ...Option) momo.Driver

    DSN: postgres://user:password@host:5432/dbname?sslmode=verify-full. Use sslmode=disable for local development only.

    With database/sql: pgxdriver.FromConnConfig(cfg *pgx.ConnConfig, opts ...Option) (*sql.DB, momo.Driver) or pgxdriver.FromSQLDB(db *sql.DB). These have no Batch or COPY path.

    Existing transactions: db.AdoptTx(pgxdriver.SQLTx(sqlTx)) and db.AdoptTx(pgxdriver.PgxTx(pgxTx)) run momo inside a transaction the caller began (Commit and Rollback return ErrAdoptedTx; the caller finishes it), and pgxdriver.UnwrapSQLTx(tx) or pgxdriver.UnwrapPgxTx(tx) give legacy code the *sql.Tx or pgx.Tx behind a *momo.Tx. Committing or rolling back the unwrapped handle of a momo-begun transaction is not allowed; momo still owns it. An adopted pgx.Tx keeps Batch (relation loading pipelines) and COPY; COPY is always binary, so vector columns need the pgvector codec on the caller's connection (ConfigureVectors on the pool, or your own AfterConnect). An adopted *sql.Tx has neither. PgxTx accepts the options of New; an exec mode that WithExecMode rejects makes every statement, batch and COPY on the adopted transaction return ErrUnsupported, as with New.

    Vectors need the pgvector vector extension in the database. The generated migration emits CREATE EXTENSION IF NOT EXISTS "vector" when a model has a vector column (see vectors.md).

    PgBouncer (transaction pooling): pgxdriver.New defaults to pgx.QueryExecModeExec (unnamed statements), and the CI PgBouncer tests open a pool and use New(pool) with that default, so no setting is needed. With FromConnConfig the exec mode is cfg.DefaultQueryExecMode, which pgx defaults to CacheStatement (not PgBouncer-safe), so set cfg.DefaultQueryExecMode = pgx.QueryExecModeExec before calling it; its opts have no effect.

    Secrets in errors, hooks and connections¶

    • Argument masking: with WithArgLogging, a value bound from a column tagged sensitive reaches hooks as momo.RedactedArg, not the value. This covers insert values, Column.Set and SetExpr assignments on insert, update and upsert (every argument inside an expression assigned to a sensitive column), the primary-key and version predicates of a model update or delete, keyset After values, and WHERE predicates in which a sensitive column is one operand: the comparison methods, EqExpr and the other expression comparisons, In, NotIn, Between, Like, ILike, ContainsLiteral, arrayop.Contains, arrayop.ContainedBy, arrayop.Overlaps, arrayop.AnyOf, and the same methods on an expression that reads a sensitive column such as sqlfn.Lower of it. Relation loading, Link, Unlink, Replace and Count mask key values bound to sensitive key columns, including join-table columns that map to them. The database still receives the real value. QueryEvent.Args is always a copy, so a hook cannot replace or reorder the bound arguments. The copy is deep for []byte and json.RawMessage values only, so changing those in place does not reach the driver; other mutable argument types are shared. Known gaps: arguments passed to raw momo.SQL or momo.TypedSQL fragments are not masked, because Momo cannot tell which column they belong to; SQLite renders values in an ON CONFLICT target predicate as SQL literals, so such a value appears in QueryEvent.SQL. Do not enable argument logging where raw fragments or conflict-target predicates carry secrets. Error.Detail() is also unmasked: it returns the raw driver detail, which for a PostgreSQL constraint violation quotes the offending key values, including sensitive ones. Do not log it or return it to clients; Error() is the safe text.
    • Encode errors: the pgx driver withholds the text of pgx client-side encode failures, which quote the bound value, on every path (pool, transactions, pinned and adopted connections, the database/sql adapter, rows). The message keeps the argument position, such as args[2]; the original error stays reachable with errors.Is, errors.As and Unwrap. That unwrapped cause still contains the bound value, so code that logs every link of an error chain must not print the causes.
    • Simple protocol: pgxdriver.WithExecMode, FromConnConfig and FromSQLDB refuse simple protocol, which interpolates values client-side, with ErrUnsupported. FromConnConfig checks the config it is given. FromSQLDB cannot read the pgx config of an opaque *sql.DB, so it checks the first connection it uses, on the first statement, not at construction. Only that first connection is checked: a custom connector that varies the exec mode per connection is not checked.

    Multi-tenant row-level security¶

    Row-level security (RLS) policies usually read a setting such as current_setting('app.tenant_id', true). The fail-closed pattern sets that setting at the start of every transaction from a scope carried in the context.Context, so a statement that forgot its scope matches no rows. WithTxSetup and WithImplicitTx build that into the *DB:

    db := momo.New(pgxdriver.New(pool),
    momo.WithTxSetup(func(ctx context.Context, tx *momo.Tx) error {
        id, ok := tenantFrom(ctx)
        if !ok {
            return nil // no scope: nothing is set, the policy matches no rows
        }
        return momo.SetConfigLocal(ctx, tx, "app.tenant_id", id)
    }),
    momo.WithImplicitTx(),
)

    ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
ALTER TABLE documents FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON documents
  USING (tenant_id = nullif(current_setting('app.tenant_id', true), '')::bigint)
  WITH CHECK (tenant_id = nullif(current_setting('app.tenant_id', true), '')::bigint);

    Connect as a role without BYPASSRLS that does not own the tables (or use FORCE, as above): superusers and BYPASSRLS roles skip every policy.

    Feature Behavior
    WithTxSetup The function runs right after every transaction momo begins: DB.Begin, DB.Tx, and the transactions momo opens itself (chunked inserts, graph creation, relation writes, vecsearch.With, implicit transactions). It runs once per real transaction, not per savepoint, and not for AdoptTx (the caller began that transaction). An error rolls back and is returned.
    WithImplicitTx Auto-commit statements on a *DB (Select, Insert, Update, Delete, Exec, Scalars, relation loads) each run in a short transaction, so the setup applies. Iter, Each and Rows hold the transaction until exhausted or closed, then commit; a scan or driver error rolls back, and so does a cancelled context for a write or a read abandoned early (a fully drained read still commits). Close early-abandoned rows to free the connection.
    SetConfigLocal set_config(key, value, true): the setting ends with the transaction. The same as Tx.SetLocal.
    Not used on an implicit *DB Pipelined relation loading (Batch) and the raw driver COPY path, because they bypass the setup (InsertQuery[T].Copy instead runs in its own transaction). BatcherOf and CopierOf report none for such a *DB; use a Tx for them.

    A behaviour change for WithImplicitTx on an unpinned *DB only: the rows of an Insert, Update or Delete with RETURNING (Rows) must be read to the end before Close. A write closed unread, or after reading only the first row (for example UpdateQuery.Rows or DeleteQuery.Rows users who read one row and close), is rolled back and Close returns ErrValidation; this includes a panic that unwinds through the loop. Handles without WithImplicitTx, a Tx and a pinned OnConn handle are unaffected, and FindOrCreate, UpsertByPK and CreateGraph read to the end themselves.

    Without WithImplicitTx, auto-commit statements on a *DB run outside any transaction, so the setup never applies to them and they are unscoped. Use WithImplicitTx (or DB.Tx) whenever the setup enforces a security boundary. Statements run through db.Driver() bypass momo and its hooks entirely, so they are never scoped either.

    The setup does not cover everything. AdoptTx transactions are the caller's, so apply the setting yourself. momo migrate and Go migrations run outside the *DB options, so they are never scoped; run them as a role that may bypass the policies. A handle from OnConn cannot begin a transaction, so on a *DB configured with WithTxSetup its statements fail with ErrUnsupported instead of running unscoped, and it reports no COPY or Batch path. A panic in a setup function rolls the transaction back before it propagates, and a panic in an Each or Iter callback rolls back the implicit transaction. If the context is cancelled before a streaming implicit write is closed, the write is rolled back and Close and Err return the context error.

    Behind PgBouncer in transaction mode use only transaction-local settings (SetConfigLocal), never a session-level SET: the session belongs to whichever client PgBouncer hands the backend to next. TestImplicitTxPgBouncer runs concurrent tenants through PgBouncer and checks no scope leaks.
